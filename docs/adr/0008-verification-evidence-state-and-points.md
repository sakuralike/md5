# ADR-0008：验证证据、状态事件与积分结算边界

- 状态：已接受
- 日期：2026-08-02
- 对应需求：SUB-06、VERIFY-01～07

## 背景

M2 第 1 次迭代已经能够创建 `pending` 候选和待结算积分，但候选状态仍依赖测试直接修改，缺少可审计的反馈历史、独立证据计算和首次验证结算。若直接覆盖反馈或候选状态，将无法解释状态来源，也容易在重试、重复贡献和反馈修改时重复发放积分。

## 决策

1. 使用 `candidate_feedbacks` 保存每个账号对每个候选的唯一当前有效反馈，数据库唯一约束为 `(candidate_id, user_id)`。
2. 每次创建或修改反馈都向 `verification_evidence_events` 追加不可变历史；提交与当前结果相同的反馈不新增历史事件。
3. 自动规则以不可变代码配置 `verification-v1` 运行，并把规则版本写入反馈、证据历史和状态事件。阈值变更必须发布新版本，不回写历史证据。
4. 独立性按“安装实例摘要 → IP 网段 → 账号”的优先级生成关联键；同一关联键在同一结果方向只计一次最高权重。Web 反馈尚无安装实例，因此当前使用 IP 网段或账号。
5. `verification-v1` 要求至少两个独立成功证据且失败权重低于 2.0 才进入 `verified`；三个独立失败证据或失败权重达到 3.0 时进入 `quarantined`。
6. 所有自动状态变化追加到 `record_state_events`，记录前后状态、原因、规则版本、触发证据和证据快照。普通用户不能直接编辑状态事件。
7. 候选首次进入 `verified` 时，只结算最早贡献的待结算积分；当时已有的后续重复贡献流水标记为 `reversed`，首次验证后新建的重复贡献流水立即标记为 `reversed`。参与首次验证的当前有效成功反馈各获得一条唯一的 `verification.accepted` 已入账流水。
8. 反馈写入使用持久化 `Idempotency-Key`。并发处理通过候选行锁、唯一约束和冲突响应避免重复当前反馈、状态事件与积分。

## 后果

- 用户可以修改反馈，同时保留完整历史；查询热度和贡献次数不会被当成正确性证据。
- `verified` 和 `quarantined` 可以由可复现规则自动产生，揭示接口无需特殊分支即可暂停隔离候选。
- 当前关联去重是 M2 基础实现；M3 接入签名桌面回执后补充安装实例，M4 再加入账号关联图、时间窗口异常和人工审核。
- 积分流水仍通过状态表达待结算、入账或冲正；后续余额投影必须从流水计算，不允许无事件地直接覆盖余额。
