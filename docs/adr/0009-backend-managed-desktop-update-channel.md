# ADR-0009：后端托管桌面更新通道与显式下载入口

- 状态：已接受
- 日期：2026-08-02
- 对应需求：DESK-09～12

## 背景

桌面端已经能够在服务端最低版本门禁失败时提示升级，但缺少统一的版本来源、发布生命周期和受控下载入口。若客户端直接依赖固定外部 URL、公开目录或任意第三方下载页，将难以撤回有问题的制品，也无法把版本、完整性、签名流程和管理员操作纳入同一审计边界。

桌面客户端仍是不可信环境。后端可以证明“某个发布记录经过受控流程并匹配指定字节”，但不能仅靠元数据证明用户实际下载到的安装包已由操作系统完成 Authenticode 验证。

## 决策

1. 后端以 `desktop_releases` 维护 `(channel, platform, architecture, version)` 唯一的发布记录，生命周期固定为 `draft → published → withdrawn`。
2. 创建、列出、上传、发布和撤回操作要求管理员 RBAC、当前会话 MFA、限流和审计；匿名客户端只拥有检查更新与下载已发布制品的能力。
3. 管理员创建草稿时先声明制品文件名、字节数和 SHA-256；上传接口以原始字节流写入临时文件，边读边校验大小与摘要，通过后才原子替换目标文件。
4. 发布操作重新计算持久化制品摘要与大小。生产环境要求发布记录的代码签名状态为 `verified`，并包含签名者主题和证书指纹；该状态必须由外部发布流水线在实际验签后提供。
5. 更新检查按通道、平台和架构严格隔离，只选择最高已发布版本；响应包含最低受支持版本、强制升级标记、发布说明、完整性元数据和后端生成的下载 URL。
6. 下载接口再次限定 `published` 状态，提供不可变缓存、ETag、标准 `Digest` 和 `nosniff`；撤回后立即拒绝新下载。开发环境使用受控本地目录，生产在发布前迁移到持久卷或对象存储/CDN。
7. 桌面端启动后自动检查稳定通道，但不静默下载、不执行安装包。用户必须显式点击，由系统浏览器打开 HTTP(S) 下载入口；生产使用 HTTPS，安装前核验操作系统展示的签名者。

## 后果

- 最低版本门禁和升级入口共享同一后端版本事实来源，管理员可以撤回有问题的版本并保留完整操作审计。
- 发布记录和 SHA-256 能检测误传、截断和存储损坏，但不能替代 Authenticode、本地证书链验证或发布机密钥保护。
- 首版没有分批发布、差分包、静默安装、客户端内置下载器和自动回滚；这些能力需要独立威胁建模、签名流水线与 Windows 10/11 实机验收后再实施。
