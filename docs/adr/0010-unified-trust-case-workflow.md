# ADR-0010：统一举报与申诉信任案件工作流

- 状态：已接受
- 日期：2026-08-02
- 对应需求：用户中心申诉入口、管理端举报与申诉、M4 信任闭环

## 背景

候选内容举报和贡献审核申诉都需要提交原因、进入管理队列、记录处理状态并向提交者展示结果。如果分别建立两套表、路由和管理页面，会重复实现对象级权限、幂等、限流、状态机和审计规则，并使同一候选相关案件难以关联。

举报/申诉案件与候选状态又不是同一个聚合：案件描述“某个问题如何被受理和结案”，候选状态描述“候选是否可见、可揭示以及证据可信度”。若结案时直接隐式修改候选状态，将绕过既有 `moderation-v1` 原因码、证据快照和状态事件边界。

## 决策

1. 使用 `trust_cases` 统一存储 `report` 和 `appeal`，使用 `trust_case_events` 保存创建与每次状态变化的不可变时间线。
2. 案件状态固定为 `open`、`in_review`、`resolved`、`dismissed`。允许打开案件进入审核或关闭、审核中案件退回打开或关闭、已关闭案件通过 `admin.reopened` 重新打开；禁止同状态空操作。
3. 举报目标固定为已存在的候选。申诉仅允许该候选的贡献者针对 `rejected` 或 `quarantined` 候选创建；可选关联案件必须指向同一候选。
4. 用户 API 只允许创建案件和查看本人案件。管理队列、详情和状态转换要求特权角色及当前 MFA 声明。
5. 举报、申诉和管理状态转换均接入数据库持久化幂等、端点限流、受控原因码和 `request_id`。相同键与相同载荷复用结果，不同载荷复用同一键返回冲突。
6. 案件事件可保存用户说明或管理员处理说明供案件详情展示，但审计详情只保存案件类型、原因码、前后状态和事件标识，不复制自由文本或候选秘密。
7. 案件结论不自动修改候选状态。需要隔离、恢复、通过或拒绝候选时，审核员必须额外调用 `moderation-v1` 状态转换，从而产生独立的候选状态事件、证据快照和审计记录。

## 后果

- 举报和申诉共享队列、契约、权限与事件模型，后续可在同一边界增加 SLA、分派、通知和统计。
- 用户只能看到本人案件，管理员能在 MFA 会话中获得统一处理视图，降低对象级越权和重复实现风险。
- 同一业务处理可能需要先结案、再执行候选状态转换，操作步骤增加，但两个领域聚合的审计语义保持清晰，失败重试也不会产生隐式跨聚合副作用。
- 首版不包含账号申诉、自动分派、处理时限通知、候选状态编排、双人复核和批量处置；这些能力需在后续迭代中独立设计和验收。
