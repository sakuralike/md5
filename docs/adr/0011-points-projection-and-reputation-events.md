# ADR-0011：积分投影与不可变信誉事件

- 状态：已接受
- 日期：2026-08-02
- 对应需求：SUB-06、VERIFY-01～07、积分与信誉、用户中心

## 背景

现有 `points_ledger` 已能保存贡献待结算、首次验证入账和重复贡献冲正，但用户缺少可查询的余额投影；`users.reputation_score` 仍以 0 为默认值，且没有解释信誉变化来源的事件。若客户端直接读取或服务端直接覆盖余额/信誉，重试、并发和后续补偿都难以审计。

## 决策

1. 用户初始信誉分统一为 50，服务端仅允许在 0～100 范围内投影当前分数。
2. 新增 `reputation_events` 作为不可变信誉流水，记录用户、实际变化量、事件类型、引用对象、受控原因码、规则版本、前后分值和创建时间。
3. `(user_id, event_type, reference_id)` 唯一约束作为信誉事件幂等边界；写入时锁定用户投影行，并在锁内再次检查既有事件。达到 0/100 边界时仍追加实际变化量为 0 的事件，以占用幂等键，避免分值回落后旧奖励被重放。
4. `reputation-v1` 在候选首次成为 `verified` 时向首位贡献者增加 3 分，向当时有效成功验证者各增加 2 分；积分奖励和信誉变化保持分账、分表。
5. `users.reputation_score` 是从事件更新得到的读取投影，不代替不可变事件；任何后续扣减或补偿也必须追加事件。
6. 用户私有 API 分别提供积分汇总、积分流水、信誉流水和反馈/贡献统计，不允许通过参数查询其他用户。
7. Web 新增“积分与信誉”页面，展示可用/待结算/已冲正积分、信誉分、贡献/反馈统计及事件历史，不展示候选秘密。

## 后果

- 首次验证结算可以同时解释积分和信誉来源，重复请求不会重复加分。
- 用户能够自行核对积分与信誉事件，为后续管理员用户处置和申诉提供证据基础。
- 候选在首次验证后又被隔离或拒绝时的积分补偿、信誉扣减和管理员复核策略仍需独立规则版本；本 ADR 不允许直接删除或改写原始奖励事件。
