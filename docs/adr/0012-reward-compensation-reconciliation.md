# ADR-0012：奖励补偿与状态驱动校正

- 状态：已接受
- 日期：2026-08-02
- 对应需求：SUB-06、VERIFY-01～07、积分与信誉、管理端需求

## 背景

`reputation-v1` 已在候选首次进入 `verified` 时向首位贡献者和当时有效的成功验证者结算积分与信誉。候选之后仍可能因新证据或人工复核进入 `quarantined`、`rejected`，也可能恢复为 `verified`。如果直接修改或删除原始奖励流水，将破坏审计、重试幂等和用户历史解释能力；如果只改变候选状态而不校正奖励，积分与信誉又会继续体现已失效的可信结论。

## 决策

1. 新增版本化规则 `reward-compensation-v1`，以每个不可变 `record_state_events` 状态事件作为一次奖励资格重算触发器。
2. 奖励来源限定为首次验证时已获得奖励的来源：首位贡献者，以及曾产生原始验证奖励的反馈。后续新增证据不会通过恢复流程获得追溯奖励。
3. 目标状态为 `verified` 时，期望净奖励等于原始实际奖励；目标状态为 `pending`、`quarantined` 或 `rejected` 时，期望净奖励为 0。
4. 新增不可变 `reward_adjustment_events`，记录状态事件、候选、用户、奖励类型、来源引用、方向、积分实际变化、信誉实际变化、原因、规则版本和时间。
5. `(state_event_id, user_id, reward_kind, source_reference_id)` 唯一约束保证同一状态事件和奖励来源只校正一次；业务请求自身仍遵守既有 `Idempotency-Key` 边界。
6. 校正只追加新的 `points_ledger`、`reputation_events` 和 `reward_adjustment_events`，不得删除或改写原始奖励。积分使用正负已入账流水，信誉继续按 0～100 边界记录实际变化量。
7. 自动状态转换与人工状态转换都必须在同一数据库事务内依次写入状态事件、必要的首次验证奖励和奖励校正；事务任一步失败均不得留下部分结果。
8. 人工将尚未验证的候选首次改为 `verified` 时，也必须执行与自动首次验证一致的首位贡献者奖励结算。
9. 管理端候选详情可展示受控的不可变校正时间线；审计详情只保存聚合变化量和受影响账号数，不复制自由文本、候选秘密或逐个账号明细。

## 后果

- 候选在验证、隔离、拒绝和恢复之间多次流转时，奖励资格可通过追加事件收敛到当前状态，不破坏历史事实。
- 积分可精确恢复原始奖励；信誉受 0～100 边界影响，恢复和扣减记录的是当次实际变化量，因此历史路径仍可解释。
- 管理端和用户端能从不可变流水看到奖励失效与恢复原因。
- 规则仍只覆盖首次贡献者和原始成功验证者；关联账号降权、异常告警、管理员用户处罚和动态信誉权重需要后续独立规则。

## 未采用方案

- **直接更新原始积分或信誉事件**：破坏不可变审计和幂等边界。
- **按当前全部证据重新发奖**：会给首次验证后才出现的反馈追溯奖励，改变既有奖励语义。
- **异步最终一致校正**：可能短时间暴露状态与余额不一致，也增加失败补偿复杂度；当前规模下优先使用同事务同步校正。
