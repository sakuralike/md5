# ADR-0018：社区社交平台边界、事件一致性与私信安全

- 状态：已接受，分阶段实施
- 日期：2026-08-12
- 决策范围：WP5 社区完整功能

## 背景

现有社区已经完成固定板块、主题、回复、举报和 MFA 治理，但点赞、收藏、关注、公开主页、群组、动态、搜索、通知和私信尚未实现。若分别在页面中直接追加逻辑，会造成可见性规则、计数、通知、搜索索引和隐私边界不一致。

## 决策

1. 社区继续位于现有模块化单体，不拆独立微服务。
2. 全部读取通道复用统一可见性策略；列表、详情、搜索、动态和通知不得分别实现权限规则。
3. 点赞、关注等关系保存事实表，计数字段仅作为可重建投影。
4. 动态、通知和搜索更新使用数据库事务事件/Outbox，实现可重试的最终一致性。
5. 可配置板块和用户群组是不同概念：板块用于全站分类，群组用于成员关系与独立治理。
6. 私信首版为一对一、纯文本、服务端 AES-GCM 加密，不宣称端到端加密，不支持附件。
7. 普通管理员不得浏览私信正文；只有被举报消息可在 MFA 案件处理上下文中最小披露并审计。
8. 实时消息采用“REST 写入和补偿读取 + Redis Pub/Sub 唤醒 + SSE 推送”，Redis 不作为事实来源。
9. 搜索通过可替换 Provider 实现；生产优先 MySQL FULLTEXT `ngram`，部署时必须验证能力并提供有界降级。
10. 四个现有固定板块通过兼容迁移写入 `community_boards`，不破坏既有帖子和链接。

## 结果

### 正面影响

- 权限和隐私规则具有单一实现入口。
- Redis、SSE、搜索索引故障不会丢失已提交的帖子、消息和通知。
- 关系计数和搜索索引可以重建，降低并发漂移风险。
- 私信不会以明文进入数据库、日志、审计或通知摘要。

### 代价

- 需要事件/Outbox、投影校验、密钥轮换和更多迁移步骤。
- 实时聊天需要多实例 Redis 与断线补偿测试。
- MySQL 中文全文检索能力必须作为部署预检项。

## 被拒绝方案

- 直接复制 Zibll 社区源码：技术栈、许可证和安全边界不适配。
- 一开始拆社区微服务：在当前规模下增加事务、部署和可观测性成本。
- 用 Redis 保存聊天事实：无法满足持久性、审计和断线补偿要求。
- 私信明文存储：不满足项目生产秘密和最小披露基线。
- 默认开放管理员私信全文搜索：违反最小权限和用户合理隐私预期。
- 首页查询时同步生成全部通知和搜索索引：增加主事务时延且难以重试。

## 验证

- 后端权限矩阵、可见性属性、并发幂等、消息加密和 Outbox 重放测试。
- Alembic 全链路前滚、降级、重新前滚。
- Web/Admin 类型、Lint、渲染和浏览器 E2E。
- 目标环境 MySQL `ngram`、Redis Pub/Sub、SSE 重连和密钥轮换验证。
