# ADR-0019：Web 待验证池与可信桌面成功直入

- 状态：已接受
- 日期：2026-08-14
- 决策者：项目负责人、开发团队

## 背景

项目需要同时降低公开 Web 提交污染总哈希池的风险，并让已登录用户在桌面端完成真实本地验证后能够快速贡献有效结果。游客缺少稳定账号身份，登录 Web 提交也不能证明密码确实完成了解压，因此二者不能仅凭提交动作进入总哈希池。桌面端同样是可逆向环境，但服务端可以对账号、安装密钥、一次性挑战、签名、防重放、版本和时间窗口执行组合校验。

## 决策

1. `POST /api/v1/archives/submissions` 改为可选认证；游客和登录用户都必须确认授权声明。
2. 所有 Web 提交都创建或合并为 `pending` 候选，不因登录状态直接进入总哈希池。
3. 游客提交的 `submissions.user_id` 为 `NULL`，不生成积分账本、待结算积分或个人贡献记录；幂等所有者由服务端对最小化网络/客户端上下文派生私有键。
4. Web 候选至少需要 4 个经 `correlation-v1` 降权后仍独立的登录用户成功反馈，且有效失败权重低于既有阈值，才由 `verification-v3` 自动置为 `verified`。
5. 已登录用户提交的桌面成功回执，只有在安装实例有效、挑战有效且单次使用、候选绑定正确、客户端版本受支持、时钟窗口有效、ECDSA 签名正确且未重放时，才可直接置为 `verified`。
6. 桌面直入不是永久信任：后续失败证据、失败激增、隔离、人工审核、奖励校正和审计链继续生效。
7. 规则变化只影响新证据处理，不回写或删除历史证据；状态事件记录 `verification-v3` 和明确的自动转换原因。

## 结果

- 优点：开放游客贡献入口，同时把公开输入与总哈希池隔离；登录 Web 用户无法绕过多人确认；真实桌面验证路径更短。
- 成本：`submissions.user_id` 需要可空迁移；Web 候选晋级速度下降；部署后必须验证 MySQL 可空外键和匿名幂等行为。
- 风险：桌面环境仍可能被控制，因此必须保留服务端组合校验、速率限制、关联分析、后续隔离和人工处置。

## 替代方案

- 所有提交都要求登录：实现简单，但不满足游客贡献需求。
- 登录 Web 提交直接验证：无法证明本地解压成功，污染风险不可接受。
- 桌面成功仍要求四人确认：风险最低，但无法满足已验证桌面贡献快速入池的产品目标。

## 验证

- 游客 Web 提交返回 `submitter_kind=guest`、`pool_status=pending_verification`、`pending_points=0`。
- 登录 Web 提交同样保持 `pending`；前三个独立成功反馈不晋级，第四个独立成功反馈晋级。
- 通过完整服务端校验的登录桌面成功回执在第一次成功证据后晋级。
- 失败、过期、重放、撤销安装、版本不支持或签名无效的桌面回执不得直入。
