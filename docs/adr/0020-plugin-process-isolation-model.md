# ADR-0020：插件进程隔离模型与唯一通路

- 状态：已接受
- 日期：2026-09-02
- 决策范围：桌面插件宿主、Windows 审核 Runner、PDPP v1

## 背景

插件包由第三方代码组成，不能因为使用同一桌面应用就获得宿主进程的信任等级。插件需要有足够的功能表达能力，但插件进程直接访问文件、网络、注册表、令牌或其他进程会把功能扩展变成权限扩展。桌面宿主和审核 Runner 还必须对同一插件使用一致的隔离边界。

## 决策

1. 插件始终作为独立进程运行，通过 JSON-RPC 2.0 over stdio 与宿主通信；禁止把第三方插件加载进宿主进程。
2. 插件对宿主的访问只有 PDPP 与已登记的 Broker 方法；协议白名单之外的方法返回 `-32601`。
3. 文件、网络、平台 API、主题、私有存储等资源由 Broker 转译，使用宿主签发的 opaque handle 或最小化结果；插件不得收到真实路径、连接串、访问令牌或安装私钥。
4. 桌面宿主与 Windows 审核 Runner 共用同一套隔离策略和 PDPP 行为；Runner 可以增加探测，但不得放宽桌面边界。
5. 沙箱、Broker、协议和治理任一层失败时均拒绝启动或拒绝发布，不降级为宿主权限运行。

## 结果

- 插件语言与宿主语言解耦，C#、Go、Rust、Python 均可通过 PDPP 接入。
- Broker 接口数量决定可用功能面，插件 OS 权限保持最小集。
- 需要维护协议版本、方法白名单、参数 Schema、审计摘要和跨语言 conformance。

## 替代方案

- 进程内加载：性能和调用便捷，但插件可直接破坏宿主进程与令牌边界，拒绝。
- 普通子进程但不使用 Broker：仍可访问用户资源，不能满足最小权限，拒绝。
- 每个插件自定义一套隔离：桌面与 Runner 会产生边界漂移，拒绝。

## 验证

- `apps/desktop-windows.tests` 验证 AppContainer、句柄白名单、Broker opaque handle 和协议白名单。
- `tests/pdpp-conformance` 验证 C#、Go、Rust、Python 的相同行为。
- `DynamicReviewExecutor` 验证未声明命令也不能绕过宿主探测。
