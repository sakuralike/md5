# ADR-0022：参数化能力模型与 Tier 授权

- 状态：已接受，分阶段实施
- 日期：2026-09-02
- 决策范围：插件 Manifest、Broker、开发者端与管理端

## 背景

当前能力清单是字符串集合，只能表达“有或没有”。文件大小、可访问 MIME、路径拒绝、调用次数和有效期等约束如果依靠代码默认值，会造成升级时权限扩大而用户无法识别。

## 决策

1. Capability v2 使用四元组：`capability`、`constraints`、`quota`、`ttl`；v1 字符串清单继续兼容并按无额外约束解释，直到迁移完成。
2. T0 基础能力可在安装时确认；T1 用户介导能力每次调用要求用户选择或确认；T2 数据能力必须同时满足 OAuth scope、用户授权、关联的已批准第三方应用和服务端 Broker 复核；T3 高危能力默认不授予。
3. `network:internet` 不永久对第三方关闭，但只能走 T3 特批、独立风险告知、可撤销授权和更密集运行时监控；`net:fetch:allowlist` 是优先替代方案。
4. `process:spawn`、`network:listen`、`registry:write`、`credential:read`、`system:persistence`、`system:driver`、`ui:global_hook` 和 `memory:read_other_process` 属于声明即拒绝清单。
5. 版本升级若扩大能力集合或放宽约束，必须重新授权；T2/T3 调用写入不含敏感值的参数指纹、结果和耗时审计。

## 结果

- 插件可以通过安全约束获得更宽的功能面，而不是获得更多 OS 权限。
- Manifest、服务端发布校验、桌面授权 UI、Broker 和审计需要共享同一能力目录。
- 迁移期必须同时处理旧版插件和新版参数化声明。

## 替代方案

- 继续使用布尔能力：实现简单，但无法表达资源边界和配额，拒绝。
- 直接授予插件 OS 权限：功能扩展与环境失守绑定，拒绝。
- 所有能力都永久拒绝：安全但损失官方和特批场景的产品价值，拒绝。

## 验证

- 当前 v1 权限集合、市场批准交集、升级权限差异和显式拒绝项已有服务端与桌面测试。
- Capability v2 的 Schema、约束比较、配额和 TTL 属于后续 P2/P3 实施验收。
