## 1. 本轮目标与边界

本轮把受控角色变更从“关闭”推进到最小安全后端闭环：管理员提交请求，另一名管理员在当前密码 + TOTP 再认证后批准或拒绝；批准后更新角色并撤销目标账号活跃会话。

本轮只开放以下普通角色转换：

- `user → trusted_contributor`
- `trusted_contributor → user`
- `trusted_contributor → moderator`
- `moderator → trusted_contributor`
- `moderator → user`

管理员、服务账号、申请人自身和非正常账号继续受保护；管理员之间的角色变更、服务账号处置、批量处置、紧急撤权和自动升级策略仍未开放。

## 2. 数据与 API

新增 `role_change_requests` 表和迁移 `20260804_0018_n2_role_change_requests.py`。请求状态为 `pending`、`approved`、`rejected`，记录目标账号、预期角色、申请角色、申请人、复核人、原因码和不可变时间信息。

| 方法 | 路径 | 作用 | 核心门禁 |
|---|---|---|---|
| `GET` | `/admin/role-change-requests` | 分页查询角色变更请求，可按状态筛选 | 管理员 + 当前会话 MFA |
| `POST` | `/admin/users/{user_id}/role-change-requests` | 创建待复核角色变更请求 | 管理员 + 用户治理一次性再认证、允许矩阵、对象保护、幂等、审计 |
| `POST` | `/admin/role-change-requests/{request_id}/approve` | 批准请求并应用角色 | 不同管理员、状态/角色乐观并发、一次性再认证、幂等、审计、会话撤销 |
| `POST` | `/admin/role-change-requests/{request_id}/reject` | 拒绝请求 | 不同管理员、状态并发、一次性再认证、幂等、审计 |

幂等摘要不包含再认证令牌；服务端先执行请求状态、目标角色和申请人检查，再消费一次性授权。前置冲突不会消耗再认证凭据。重放同一幂等键返回原响应，新的幂等键不能重放已消费令牌。

## 3. 安全与审计

- 申请人与复核人必须是不同管理员，避免单人自提自批。
- 目标账号必须处于 `active`，且不能是管理员、服务账号或当前操作者。
- 批准前再次校验目标账号仍处于申请时的预期角色；不一致返回 `409`。
- 批准后撤销目标账号所有未过期活跃会话，确保新角色从重新登录开始生效。
- 审计记录角色转换、原因码、复核结果和撤销会话数量，不记录密码、TOTP、再认证令牌或完整个人信息。
