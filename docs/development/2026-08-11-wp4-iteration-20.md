## 1. 本轮目标

第 19 次迭代只能采集目标主机资源，不能把 API、MySQL、Redis、Celery 操作窗口和单 Worker 故障时间线合并成现有 `staging-resource-samples-v1`。本轮新增完整会话编排器，使短时回归和后续 4 小时正式运行复用同一份采集、校验和降级恢复逻辑，并严格阻止不满足 profile 的会话冒充 `target-execution`。

## 2. 已实现内容

## 3. Staging 短时实测

在 `/opt/password-detective-staging` 执行 75 秒请求、实际 78 秒的目标观测，会话使用 15 秒资源采样、25 秒探针窗口和 3 个 Worker：

- 资源采样覆盖率 `100%`，最大样本间隔 `16` 秒；
- Worker 拓扑成功完成 `3 -> 2 -> 3`，恢复耗时 `0.278` 秒；
- API/MySQL/Redis/Celery 各完成 `70` 次操作，错误率 `0%`，最大连续错误均为 `0`；
- P95：API `21.618 ms`、MySQL `6.183 ms`、Redis `1.812 ms`、Celery `20.877 ms`；
- MySQL 连接峰值 `3`，允许预算 `136`；最终 Celery 队列深度 `0`；
- API CPU 采样峰值 `98.07%`，Worker 聚合 CPU 采样峰值 `196.23%`，超过 profile 的单服务聚合阈值；内存均未超限。

会话和本地复核均返回 `status=passed`，但证据保持 `target-observation / observation-only / eligible_for_target_execution=false`。未通过项为：持续时间、最小操作量、资源阈值。

## 4. 证据边界

- 78 秒结果只证明编排、采样、故障恢复和资格拒绝链路可运行，不是 4 小时容量验收；
- 当前 CPU 阈值按服务聚合，3 个 Worker 的 CPU 总和可超过 100%；下一轮必须决定继续使用聚合预算，还是基于副本数改为每副本/核归一化阈值，不能直接放宽阈值；
- 未执行 MySQL/Redis HA 切换，不能生成完整 `staging-execution-evidence-bundle-v1`；
- 未进入证据封存、四角色审批或 Go/No-Go。

## 5. 下一轮入口

先收口资源阈值口径并增加预运行容量校准，然后执行不少于 4 小时的正式 Staging 会话。正式运行必须满足 profile 的 10,000 次最低操作量、95% 采样覆盖、错误/P95/连接/队列/资源阈值，并继续完成 MySQL/Redis HA 切换；只有全部通过后才请求 `target-execution`，随后进入证据封存和四角色审批。
