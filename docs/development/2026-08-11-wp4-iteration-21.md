# WP4 第 21 次开发迭代：Staging 拓扑容量预检与资源归一化

- 日期：2026-08-11
- 范围：目标拓扑预检、数据库连接容量预算、多副本 CPU 归一化、Staging 短时校准
- 状态：实现、专项测试和 Staging 短时校准完成；API 双副本拓扑与单副本 CPU 余量仍阻塞正式 4 小时执行

## 1. 本轮目标

第 20 次迭代已经证明长时会话编排链路可运行，但把多 Worker 的 CPU 聚合值直接与单服务 `80%` 阈值比较，导致三副本 Worker 的 `196.23%` 被误判为超限；同时会话没有在执行前证明 Staging 实际运行了 profile 要求的 `2 API + 3 Worker + 1 Scheduler`。本轮将资源口径和实际拓扑变成显式合同，在进入 `target-execution` 前同时校验运行副本、依赖可用性与数据库连接容量。

## 2. 已实现内容

- 新增 `staging-topology-capacity-preflight-v1`：
  - 通过 Compose 发现 API、Worker、Scheduler、MySQL、Redis 的实际运行数量；
  - 只输出服务级计数，不记录容器名、容器 ID 或连接信息；
  - 要求 API/Worker/Scheduler 与 profile 精确一致，MySQL/Redis 至少有一个运行实例；
  - 按所有 API、Worker、Scheduler 客户端进程计算数据库连接池请求量、允许预算与剩余余量。
- 新增 `scripts/staging-topology-preflight.ps1`、`pnpm staging:topology-preflight`、专项测试和统一门禁接入。
- readiness profile 新增版本化资源核算口径：
  - CPU：`per-running-replica-average`，即服务聚合 CPU 除以该样本的实际运行副本数；
  - 内存：`service-aggregate`，保留服务全部运行副本的聚合峰值；
  - 每个资源样本必须包含服务副本计数，缺失计数不得生成合格证据。
- 稳定性会话在扩展 Worker 后立即生成拓扑预检，并将其纳入会话来源、资格判定和敏感字段检查；命令行 Worker 数量必须与 profile 一致。
- Prometheus 平台导出合同同步增加 API、Worker、MySQL、Redis 四个运行副本数序列，共 14 个规范化序列；适配器拒绝缺失或为零的副本计数。
- 最终资源趋势物化器与证据校验器同步采用相同核算口径，避免短时会话、平台导出与正式证据包出现不同算法。

## 3. Staging 短时校准

在 `/opt/password-detective-staging` 执行 75 秒请求、实际 77 秒的短时目标观测，使用 15 秒资源采样、25 秒探针窗口和 3 个 Worker：

- 实际拓扑为 `1 API + 3 Worker + 1 Scheduler + 1 MySQL + 1 Redis`；profile 要求 `2 + 3 + 1`，因此拓扑预检只因 API 少一个副本而失败；
- 数据库预算为 11 个客户端进程、每进程最多 10 个连接、请求 110、允许 136、剩余 26；容量预算通过；
- 四类操作各完成 70 次且错误率为 `0%`；P95 为 API `12.682 ms`、MySQL `6.732 ms`、Redis `1.805 ms`、Celery `16.427 ms`；
- Worker 成功完成 `3 -> 2 -> 3`，恢复耗时 `0.284` 秒；采样覆盖率 `100%`，最大样本间隔 `15` 秒；
- Worker 聚合 CPU 峰值 `196.35%`，按 3 个运行副本归一化为 `65.45%`，正确通过 `80%` 阈值；聚合内存峰值约 `482.9 MiB`；
- API 单副本聚合/归一化 CPU 峰值均为 `98.63%`，仍超过 `80%`，不是核算误差；MySQL、Redis 和数据库连接/最终队列均通过。

结果严格保持 `target-observation / observation-only / eligible_for_target_execution=false`。未通过项为持续时间、最小操作量、API 目标拓扑和 API CPU 余量。

## 4. 当前阻塞与架构结论

- 当前根 Compose 给 API 配置固定宿主机端口 `${API_PORT:-8000}:8000`。在同一主机直接扩展到两个 API 副本会产生端口冲突，无法满足 profile 的目标拓扑。
- 正式 4 小时执行前必须增加反向代理/负载均衡入口，使多个 API 副本仅暴露容器内部端口，由单一入口承接探针和监控；不能通过把 profile 改回单副本来规避目标拓扑。
- API 单副本短时 CPU 峰值已超过阈值。双副本拓扑就绪后需先重复短时校准，确认负载分摊后的每运行副本平均 CPU 小于等于 `80%`，再启动 4 小时正式执行。
- 本轮未执行 MySQL/Redis HA、证据封存或四角色 Go/No-Go，不能形成生产放行结论。
