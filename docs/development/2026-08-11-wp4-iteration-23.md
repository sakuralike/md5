# WP4 第 23 次开发迭代：Staging API 双副本入口与监控发现

- 日期：2026-08-11
- 范围：Staging API 多副本 Compose overlay、loopback 反向代理、Prometheus 多目标发现、拓扑与短时资源校准
- 状态：本地实现、专项验证、目标 Staging 部署与短时校准完成；正式 4 小时会话与 MySQL/Redis HA 仍待执行

## 1. 本轮目标

第 21 次迭代确认根 Compose 的 API 固定宿主机端口会阻止同主机扩展到两个副本。本轮保持根开发拓扑不变，增加 Staging 专用 overlay，使 API 只暴露容器内部端口，由单一 loopback 入口承接探针；同时让 Prometheus 独立发现两个 API 实例，并在正式 4 小时会话前完成短时校准。

## 2. 已实现内容

- 新增 `infra/staging/docker-compose.staging.api-ha.yml`：
  - 使用 `!reset` 移除 API 的宿主机端口发布，允许 `docker compose --scale api=2`；
  - API、Worker、Scheduler 共用同一候选运行镜像，避免三类服务并行重复构建；
  - API 副本只启动 Uvicorn，不再并发执行 Alembic；迁移改为扩容前的一次性任务；
  - 新增固定版本 Nginx `api-proxy`，仅将 `${API_PORT}` 绑定到 `127.0.0.1`。
- 新增 `infra/staging/nginx.api-ha.conf`：使用 Docker 内置 DNS 动态解析 `api` 服务，将请求分配到健康 API 副本；关闭访问日志且不向客户端暴露上游容器地址。
- Staging Prometheus 改用 DNS 服务发现抓取所有 API A 记录，并补齐稳定的 `service=api`、`environment=staging` 标签。
- 新增 `staging-api-ha-overlay-v1` 静态合同、PowerShell 合同入口、5 项正负向测试和统一门禁接入。
- 监控 smoke 新增期望 API target 数量参数；API HA smoke 串联反向代理 readiness、`2 API + 3 Worker + 1 Scheduler` 拓扑容量预检和两个 Prometheus API target。

## 3. 本地隔离运行验证

使用合成 Secret、隔离端口和独立 Compose project 从空数据卷完成：

1. 候选 API 镜像单次构建；
2. MySQL/Redis 健康后执行一次性 `alembic upgrade head`；
3. 启动 `2 API + 3 Worker + 1 Scheduler + 1 API Proxy` 及 Prometheus、Grafana、Alertmanager、隔离通知接收器；
4. 反向代理 readiness、拓扑预检和监控 smoke 全部通过，Prometheus 同时发现两个健康 API target；
5. 完成 78 秒短时稳定性校准和 `3 -> 2 -> 3` Worker 恢复演练。

短时校准结果：

- 四类操作各 70 次，错误率 `0%`；
- API P95 `8.459 ms`，MySQL P95 `18.496 ms`，Redis P95 `17.333 ms`，Celery P95 `5.562 ms`；
- API 两副本聚合 CPU 峰值 `146.67%`，每运行副本平均 `73.335%`，低于 `80%` 阈值；
- Worker 恢复耗时 `0.454` 秒，最终队列深度为 `0`；
- 数据库连接峰值 `4`，允许预算 `136`，拓扑和资源阈值通过。

该结果仍是 `target-observation / observation-only`，仅因持续时间和操作量不足而不具备正式目标执行资格，不得替代不少于 4 小时的 Staging 会话。

## 4. 安全与运维边界

- 反向代理、Prometheus、Grafana、Alertmanager 和通知接收器保持 loopback 绑定；本轮不增加域名或 HTTPS 配置。
- 多副本启动前必须先运行一次性迁移；禁止由多个 API 副本同时抢跑 Alembic。
- 监控必须看到恰好两个健康 API target，不能只验证代理自身健康。
- 所有验证数据为合成数据，报告不记录密码、令牌、连接串、容器 ID 或内部上游地址。
