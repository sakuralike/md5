# WP4 第 24 次开发迭代：正式 Staging 长时会话后台控制与状态收口

- 日期：2026-08-11
- 范围：正式不少于 4 小时的 Staging 稳定性会话后台启动、并发互斥、进程身份校验、完成状态与证据摘要
- 状态：代码与自动化门禁完成；目标 Staging 部署后启动正式会话，最终结论须等待真实 4 小时窗口结束

## 1. 本轮目标

第 23 次迭代已关闭双 API 拓扑、loopback 代理、双监控 target 和短时资源校准缺口。本轮不改变稳定性证据合同，而是为真实 4 小时执行提供可脱离 SSH 会话持续运行的控制入口，避免重复启动、PID 复用误判、证据目录覆盖或会话结束后状态无法收口。

## 2. 已实现内容

- 新增 `scripts/control_staging_formal_session.py`：
  - `start` 默认执行 `14400` 秒、固定窗口 `300` 秒、每 `15` 秒采样，并在第 `3600` 秒执行一次 `3 -> 2 -> 3` Worker 恢复事件；
  - 默认叠加根 Compose、Staging override、API HA、监控和 Staging 监控五个 Compose 文件；
  - 默认请求 `target-execution`，少于 4 小时的调试执行必须显式使用隐藏测试开关，正常入口不能将短时结果冒充正式证据；
  - 每次运行生成不可复用的 UTC 时间戳加随机标识目录，避免覆盖既有证据；
  - 使用独占状态锁阻止并发正式会话，并在锁持有进程消失后安全回收陈旧锁；
  - 保存 supervisor PID 与 Linux `/proc` 启动标记，降低 PID 被复用时误判为原会话仍存活的风险；
  - supervisor 与 SSH 会话分离，标准输出和错误输出写入权限受限日志；运行结束后原子更新状态文件；
  - `status` 可将异常退出但未写最终状态的会话收口为 `interrupted`，并在证据存在时绑定验证文件 SHA-256、执行资格、持续时间、错误率、覆盖率和队列结果。
- 新增 `pnpm staging:formal-session` 入口。
- 新增 6 项单元测试，覆盖正式参数、目标执行标记、Compose 拓扑、状态脱敏、陈旧 supervisor 收口、验证摘要哈希和 PID 启动标记。
- 将控制器、测试和 API HA 合同纳入 `check.ps1 -IncludeStagingSession`。

## 3. 安全与完整性边界

- 控制状态不持久化环境变量、连接串、密码、令牌、Secret 或请求数据，只记录执行元数据和非敏感命令参数。
- 状态文件、日志和运行目录在支持 POSIX 权限的平台上分别限制为 `0600`、`0600` 和 `0700`。
- 控制器仅保证会话执行和证据状态完整性；正式通过仍必须由既有 `staging-stability-session-verification-v1` 验证器确认 `eligible_for_target_execution=true`。
- `completed` 表示 runner 完整结束；是否具备目标执行资格必须读取状态中的 `verification.eligible_for_target_execution`，不能只看进程退出。
- 本轮不配置域名或 HTTPS，不引入真实账号、真实密码或真实令牌。

## 4. 目标执行命令

```bash
python3 scripts/control_staging_formal_session.py start \
  --source-revision <candidate-commit>
```

查询状态：

```bash
python3 scripts/control_staging_formal_session.py status
```

正式会话结束后，只有状态为 `completed`，且 `verification.verification_status=passed`、`verification.eligible_for_target_execution=true`，才可进入 MySQL/Redis HA 切换与证据封存。

## 5. 下一轮入口

1. 等待并复核正式 4 小时会话最终证据；
2. 若任一资源、业务操作、恢复或容量检查失败，保留证据并先修复，不得自动进入 HA；
3. 正式稳定性证据通过后，依次执行 MySQL HA、Redis HA 切换；
4. 汇总资源、稳定性、HA 与回滚证据，封存并交给自动发布证据门禁输出结论。
