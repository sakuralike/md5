## 1. 本轮目标

正式 4 小时稳定性会话仍在后台运行。本轮不提前触发数据库或缓存故障，而是补齐 HA 执行入口的机器门禁，防止操作人员仅凭进程退出、旧证据或合成夹具绕过稳定性验收直接执行 MySQL/Redis 切换。

## 3. 使用方法

MySQL 预检：

```bash
python3 scripts/control_staging_ha_execution.py \
  --dependency mysql \
  --write-checksums
```

需要把未就绪作为命令失败时增加 `--require-ready`，此时 `blocked` 返回退出码 `2`；默认模式仍会生成可审计的阻断报告并返回成功。

Redis 预检：

```bash
python3 scripts/control_staging_ha_execution.py \
  --dependency redis \
  --mysql-report .local/staging-target-execution/mysql-ha-failover-report.json \
  --write-checksums \
  --require-ready
```

## 4. 安全与执行边界

- 门禁只决定是否允许进入故障切换步骤，不执行云平台、数据库或 Redis 的实际故障动作。
- 正式稳定性状态为 `running`、`failed` 或 `interrupted` 时必须保持 `blocked`。
- 验证文件被移动、重写或摘要不一致时必须保持 `blocked`。
- Redis 不得与 MySQL 并行演练；必须先生成 MySQL 的真实目标执行证据。
- 人员签字不是发布条件，后续仍由 `automated-evidence-gate` 基于完整机器证据输出结论。
