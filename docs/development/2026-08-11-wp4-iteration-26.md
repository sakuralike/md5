# WP4 第 26 次开发迭代：托管 HA 目标能力证明与单节点防提升

- 日期：2026-08-11
- 范围：MySQL/Redis HA 目标能力证据、托管/哨兵拓扑约束、RTO/RPO 能力校验和执行门禁接入
- 状态：代码、合同夹具和自动化测试完成；目标 Staging 仍需真实托管 HA 平台导出

## 1. 本轮目标

第 25 次迭代已将 HA 执行绑定到正式稳定性证据，但尚不能证明目标 MySQL/Redis 本身具备 profile 声明的 HA 能力。当前 Staging 使用单 MySQL、单 Redis 容器，不能因为应用层稳定性通过就被提升为 `managed-ha`。本轮增加独立能力证据，关闭这一错误放行路径。

## 2. 已实现内容

- 新增 `scripts/verify_staging_ha_target_capability.py` 和 `staging-ha-target-capability-v1`：
  - MySQL `managed-ha` 必须是托管服务、至少两个故障域、至少一个备用副本、自动切换、稳定应用地址、监控、备份和 PITR 均启用；
  - Redis 支持托管服务或自管 Sentinel；Sentinel 模式至少三个 Sentinel，并同样要求跨故障域、副本、自动切换、稳定应用地址、监控和持久化；
  - 声明的 RTO/RPO 不能高于 readiness profile；
  - 六项运行检查必须全部为真；
  - 禁止端点、主机名、连接串、密码、令牌和 Secret 进入能力报告。
- 新增 MySQL、Redis 合同示例，只能标记为 `contract-fixture`。
- 扩展 `control_staging_ha_execution.py`：
  - 新增 `--capability-report`；
  - 缺失、无效或合同夹具能力报告均保持 `blocked`；
  - 只有真实平台导出的 `target-observation` 能满足能力检查。
- 新增 `staging-ha-capability-contract.ps1`、`pnpm staging:ha-capability-contract`、10 项新增测试；与第 25 次门禁测试合计 17 项。
- 更新统一门禁与 GitHub Actions，上传能力合同验证和 SHA-256。

## 3. 运行方式

合同验证：

```powershell
pnpm staging:ha-capability-contract
```

真实 MySQL 能力导出验证后再执行门禁：

```bash
python3 scripts/control_staging_ha_execution.py \
  --dependency mysql \
  --capability-report /secure-export/mysql-ha-target-capability.json \
  --write-checksums \
  --require-ready
```

真实报告必须使用 `evidence_kind=target-observation`，且 `source_adapter` 不能包含 fixture、synthetic、mock 或 test。

## 4. 当前结论

- 单节点 Docker Compose 不是 MySQL `managed-ha`，也不是 Redis Sentinel/托管 HA。
- 合同示例只验证字段、约束和工具链，不能作为目标能力证明。
- 正式稳定性会话完成后，如果仍未取得真实托管 HA 能力导出，MySQL 门禁必须继续保持 `blocked`。
- 本轮不触发任何数据库、缓存或云平台故障动作。

## 5. 下一轮入口

1. 等待正式稳定性会话完成并复核最终证据；
2. 确定可执行的托管 MySQL HA 和 Redis Sentinel/托管 HA 目标；
3. 从目标平台导出脱敏 `target-observation` 能力报告；
4. 能力门禁与正式证据同时通过后，才执行 MySQL HA；MySQL 目标证据通过后再执行 Redis HA。
