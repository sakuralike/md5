# WP4 第 29 次迭代：完整用户等级系统

- 日期：2026-08-11
- 范围：成长值事实、等级投影、自动成长、权益门禁、配置治理、Web/Admin 展示
- 权限边界：用户等级不是产品角色，不自动授予审核员或管理员权限

## 目标

在既有积分与信誉体系之外建立独立、可审计、可重建的用户等级系统，使成长规则、等级目录和等级权益形成后端事实、运行时授权、用户端展示、管理端治理和自动化测试的完整闭环。

## 后端与数据模型

1. 新增 `user_growth_events` 不可变成长流水，使用 `(user_id,event_type,reference_id)` 唯一约束保证业务幂等。
2. 新增 `user_level_profiles` 当前等级读取投影，保存成长值、等级编码/名称、规则哈希和评估时间；投影可由成长流水和当前规则重建。
3. 新增 Alembic 迁移 `20260811_0025_user_levels.py`。
4. 默认成长规则：每日首次成功登录 `+5`、贡献候选首次成为 `verified` `+100`、有效验证被接受 `+25`。
5. 候选奖励失效、恢复或再次失效时追加成长补偿事件，与积分/信誉补偿保持同一状态驱动语义，不删除原始奖励。

## 等级与权益

| 等级 | 最低成长值 | 默认每日揭示额度 | 默认允许贡献 |
|---|---:|---:|---|
| 新手侦探 | 0 | 20 | 是 |
| 见习侦探 | 100 | 30 | 是 |
| 资深侦探 | 500 | 50 | 是 |
| 专家侦探 | 1500 | 75 | 是 |
| 首席侦探 | 5000 | 100 | 是 |

- 每日揭示额度取系统全局基线与等级额度的较大值，避免错误配置降低既有全局保障。
- `can_submit` 在创建贡献时由 API 强制校验，不能仅依赖前端控制。
- 等级升级或降级只改变成长展示和上述权益，不改变 `UserRole`。

## 配置治理

- `OperationalSettingsSnapshot` 新增 `user_levels`。
- 等级编码和阈值必须唯一，首级阈值必须为 0，阈值必须严格递增。
- 管理端通过既有配置草稿、发布、回滚流程维护等级规则。
- 发布或回滚时刷新运行时设置、重建全部用户等级投影，并在审计详情中记录 `rebuilt_level_profiles`。

## API 与界面

- `GET /api/v1/me/level`：当前等级、下一等级、进度、差额和权益。
- `GET /api/v1/me/level-catalog`：当前生效等级目录和规则哈希。
- `GET /api/v1/me/growth-events`：本人成长值不可变流水。
- `GET /api/v1/me/trust-profile`：增加等级摘要。
- Web 信誉中心升级为“用户等级、积分与信誉”，展示等级进度、下一等级、权益和成长流水。
- Admin 系统配置页支持等级规则增删改与排序归一化；用户治理详情展示当前等级和成长值。

## 交付边界

- 本轮不引入积分商城、付费会员、人工授予等级或角色自动晋升。
- 等级规则虽然可配置，但只能通过不可变配置版本治理，不能直接修改单个用户等级。
- 生产数据库升级仍须在目标环境按迁移和回滚流程执行；本地通过不替代目标环境验收。
- 远端同步在提交后通过 GitHub Git Data API 等效完成。
