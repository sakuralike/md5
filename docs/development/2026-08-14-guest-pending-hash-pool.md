# 游客待验证哈希池与 verification-v3 开发记录

**日期：** 2026-08-14
**范围：** Web、API、数据库迁移、共享契约与验证状态机；桌面 UI 不在本轮范围。

## 目标

- 未登录游客可以提交已获授权的哈希值—密码对，但只能进入待验证池。
- 登录用户通过 Web 提交时同样进入待验证池。
- Web 候选至少由 4 名经关联降权后仍独立的登录用户确认成功，才能进入总哈希池。
- 登录用户通过桌面端完成验证并提交通过服务端完整校验的成功回执时，候选直接进入总哈希池。

## 实现

### API 与数据

- `POST /api/v1/archives/submissions` 使用可选认证。
- `submissions.user_id` 改为可空；迁移版本为 `20260814_0037`。
- 游客提交不检查用户权益、不生成积分账本，审计事件允许匿名操作者并记录认证状态。
- 响应增加 `submitter_kind`、`pool_status`、`required_success_confirmations`，便于前端明确展示准入结果。
- 游客幂等域使用服务端私有派生键，不把原始 IP 或 User-Agent 写入业务响应。

### 验证规则

- 活跃规则升级为 `verification-v3`。
- 普通 Web 成功反馈采用既有 `correlation-v1` 关联降权，要求 4 个独立成功组。
- 桌面回执只有在登录、安装实例、挑战、防重放、版本、时间窗口、候选绑定和 ECDSA 签名均通过后，才以可信桌面成功证据直接验证。
- 候选后续仍可因失败激增进入隔离，奖励校正和人工审核链保持不变。

### Web

- 未登录状态保留贡献表单和提交按钮。
- 页面持续展示“Web 统一待验证、至少 4 名不同登录用户确认、桌面签名成功直入”的规则。
- 游客成功提示明确无个人历史和积分；登录用户提示待验证积分将在晋级后结算。

## 自动化验收

- 游客创建与幂等重试：提交归属为空、无积分账本、匿名审计、响应为待验证池。
- 登录 Web 候选：第 1～3 个独立成功反馈保持 `pending`，第 4 个晋级 `verified`。
- 桌面回执：首个通过完整校验的成功回执直接晋级，重复回执和既有防重放负向用例保持通过。
- 关联、信誉、奖励补偿与候选隔离测试同步调整为四人门槛。

## 迁移与回滚

- 升级：将 `submissions.user_id` 改为允许 `NULL`。
- 降级：先删除 `user_id IS NULL` 的游客提交，再恢复非空约束；执行降级前必须确认这类游客提交允许被删除。
- 旧的 `verification-v1/v2` 证据与状态事件保持不可变，新材料按 `verification-v3` 处理。

## 完成定义

1. API 全量测试、Ruff、Web 测试、类型检查和 ESLint 通过。
2. Alembic 升级/降级往返和项目统一门禁通过。
3. 提交推送远端后，Staging 运行迁移 `20260814_0037`。
4. Staging 真实请求验证游客待验证、四人晋级和桌面成功直入。
## Staging 回归修复

- 真实 Staging 四个独立来源验收发现：游客候选达到 `verification-v3` 门槛后，奖励结算仍尝试向空 `user_id` 写入贡献信誉/成长事件，触发数据库非空约束并返回 HTTP 500。
- 现已将贡献者信誉与成长奖励限定为存在 `user_id` 的首个提交；游客晋级不产生个人贡献奖励，但仍正常结算四名登录验证者的积分、信誉和成长奖励。
- 新增游客提交达到四人门槛的 API 回归测试，覆盖候选晋级、匿名提交保持空用户归属，以及不生成 `contribution.verified` 奖励事件。
