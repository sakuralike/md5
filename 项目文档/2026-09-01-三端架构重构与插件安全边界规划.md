# 三端架构重构与插件安全边界规划

- 版本：v1.0
- 日期：2026-09-01
- 适用范围：桌面宿主端（`apps/desktop-windows`）、Web 开发者端（`apps/web`）、Web 插件管理端（`apps/admin` + `apps/api/modules/desktop_plugins`）
- 关联文档：《密码侦探社项目规格说明书-v3.0.md》《桌面插件开发指南与SDK.md》《第三方桌面端API-v1设计说明-2026-08-15.md》
- 状态：实施中；P0 的 D1、D2、D3、D5 已实现

## 1. 结论先行

**核心判断：本项目不需要、也不应该对桌面端做语言级重写。需要重构的是分层与边界，不是技术栈。**

三条支撑理由：

1. **插件生态与宿主语言已经解耦。** PDPP v1 采用「独立进程 + JSON-RPC 2.0 over stdio」，`tests/pdpp-conformance` 已强制 C# / Go / Rust / Python 四语言矩阵在真实 AppContainer 中跑通。宿主语言的唯一职责是「起进程、管管道、做代理、渲染 UI」，与插件能写什么毫无关系。换宿主语言对插件能力上限的贡献为零。

2. **最有价值的资产是 Windows 沙箱代码，而这部分几乎是语言绑定的。** `Plugins/Windows/WindowsSandboxedProcess.cs`（1047 行 P/Invoke）实现了 AppContainer、Job Object、目录 ACL、环境净化、句柄继承白名单五重机制，且已被一致性测试与动态审核流水线实际验证。这部分重写 = 把已验证的安全资产清零重来，风险远大于收益。

3. **当前真正的风险是逻辑性的，不是语言性的。** 按严重度排序：网络/注册表隔离依赖 AppContainer 默认行为（隐式）、动态审核 canary 可被未声明命令绕过（检测盲区）、`UseAppContainer=false` 缺少显式策略门禁（单点降级）、19 篇 ADR 与威胁模型对插件系统零覆盖（治理真空）。这四个问题换任何语言都会原样存在。

**本规划的主线**：保留 C#/.NET 技术栈，按「安全内核下沉 + 能力面拓宽 + 边界显式化 + 治理补齐」四步重构，同时把沙箱层抽成可被桌面端与审核 Runner 共用的独立组件，为未来跨平台预留接口而非预留实现。

## 3. 重构目标与设计原则

### 3.1 目标

1. **能力面最大化，权限面最小化。** 插件可做的事由宿主暴露的接口数量决定；插件进程自身的 OS 权限恒定为最小集。
2. **边界显式化。** 所有安全约束从「默认行为」升级为「显式策略 + 启动断言 + 测试覆盖」。
3. **三端职责单一。** 桌面端只做执行与隔离，Web 开发者端只做身份与供给，管理端只做审核与治理。
4. **治理可追溯。** 架构决策、威胁模型、权限变更全部文档化并与实现同步。

### 3.2 原则

- **P1 单一通路（Sole Path）**：插件对宿主的一切访问必须经由 Broker；对 OS 的一切访问必须经由 Broker 转译。协议层白名单之外的方法一律 `-32601`。
- **P2 能力即令牌（Capability as Token）**：权限不是布尔开关，而是「能力标识 + 参数约束 + 有效期 + 配额」的四元组（§4.3）。
- **P3 默认拒绝（Deny by Default）**：未在任何能力清单中出现的资源类型，宿主不得提供任何转译路径。
- **P4 隐式即缺陷（Implicit is a Bug）**：任何依赖平台默认行为实现的隔离，必须补显式规则并纳入测试。
- **P5 失效安全（Fail Closed）**：沙箱创建失败、策略加载失败、签名校验失败一律拒绝启动插件，不得降级运行。
- **P6 内核复用（One Kernel）**：桌面宿主与审核 Runner 必须共用同一份沙箱实现，禁止逻辑分叉。

## 4. 插件权限模型与安全边界设计

### 4.1 关键论断：能力面宽度 ≠ 权限面宽度

用户诉求是「插件在框架内以尽可能宽松的权限实现任意功能，同时保证安全」。这两者在进程隔离架构下**并不冲突**，但必须走对路径：

- **错误路径**：给插件进程更多 OS 权限 → 功能变多，安全边界同步塌陷。
- **正确路径**：插件进程权限恒定为最小集，**把宿主 Broker 的能力面做宽** → 功能变多，边界不变。

举例：插件要「读取用户选中的压缩包并输出风险报告」。
- 错误做法：授予文件系统读权限，让插件自己 `File.Open`。
- 正确做法：用户通过宿主文件选择器授权 → 宿主 `PluginFileBroker.GrantRead` 生成 `file_ref` → 插件只拿到 32 位十六进制句柄，通过 `host/file/read` 分块读取，**永远看不到真实路径**（本项目已实现，应作为范式推广到所有资源类型）。

**结论：宿主 Broker 的接口数量就是插件的能力上限。重构的重点是「增加 Broker 能力 + 收紧进程权限」，而不是放宽进程权限。**

### 4.2 四层防御模型

```
┌─ L4 治理层 ── 签名 · 审核 · SBOM · 撤销 · 审计 ────────────┐
├─ L3 协议层 ── 方法白名单 · Schema 校验 · 体积/深度/超时限制 ─┤
├─ L2 代理层 ── Capability Broker · 参数约束 · 配额 · 审计 ───┤
├─ L1 进程层 ── AppContainer · Job Object · ACL · 环境净化 ───┤
└─ L0 宿主层 ── 宿主自我降权 · 完整性自检 ────────────────────┘
```

各层独立失效不影响其他层。当前 L1/L2/L3 已有实现，L4 治理与 L0 宿主自保是缺口。

**L1 进程层（已有，需补强）**

| 机制 | 现状 | 重构动作 |
|---|---|---|
| AppContainer | 已实现，默认开启 | 补启动断言：策略要求沙箱时创建失败即拒绝启动（D3） |
| Job Object | 已实现（内存/CPU/进程数/ KillOnClose） | 增加 `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`；显式设 `child_processes=0` 为硬约束 |
| 目录 ACL | 已实现（安装目录 RX、工作目录 M、私有存储 M） | **新增：显式拒绝 `%WINDIR%`、其他用户配置目录、网络驱动器** |
| 环境净化 | 已实现（21 变量白名单 + 重定向） | 补测试：断言宿主秘密环境变量零泄漏 |
| 句柄继承 | 已实现（仅 3 个 stdio 管道） | 保持 |
| **网络出站** | **隐式（AppContainer 默认拒绝）** | **新增：显式 WFP 出站阻断规则 + 启动后连通性自检（D1）** |
| **注册表** | **隐式** | **新增：显式 ACL 拒绝 + 启动后写入自检（D1）** |

**L2 代理层（已有，需参数化）**：见 §4.3。
**L3 协议层（已有，需补）**：消息 ≤1MB、深度 ≤32、超时终止均已实现；补充**响应体的 Schema 校验**（当前仅校验输入，未校验输出，恶意插件可返回超长/畸形数据攻击宿主反序列化）。
**L4 治理层**：见 §5.3。
**L0 宿主层（新增）**：见 §4.6。

### 4.3 参数化能力模型（Capability v2）

当前 `capabilities` 是字符串集合（布尔型）。升级为四元组：

```jsonc
{
  "capability": "file:read:selected",
  "constraints": {
    "grant_mode": "user_pick",        // user_pick | scoped_path | none
    "max_bytes": 268435456,
    "allowed_mime": ["application/zip", "application/x-7z-compressed"],
    "path_denylist": ["**/*.exe", "**/Windows/**"]
  },
  "quota": { "per_invocation": 4, "per_day": 200 },
  "ttl": "session"                     // session | persistent
}
```

**能力分层（Tier）与授权方式：**

| Tier | 能力示例 | 授权方式 | 可否自动授予 |
|---|---|---|---|
| **T0 基础** | `ui:command`、`storage:private` | 安装时一次确认 | 是 |
| **T1 用户介导** | `file:read:selected`（宿主选择器授权） | 每次调用时用户显式选择文件 | 是（逐次授权） |
| **T2 数据访问** | `api:profile:read`、`api:hash:read` | 需 OAuth scope + 用户授权 + 关联 APPROVED 第三方应用 | 否，需服务端 `authorize_broker_capability` 全链路通过 |
| **T3 高危** | `network:internet`（**可经安全评审特批授予，默认不授予**）；`process:spawn`、`system:persistence`、`credential:read`、`system:driver`、`registry:write`（平台保留，实际不授予） | `network:internet`：平台人工审核 + 独立风险告知 + 可撤销；其余：仅限官方，不对第三方开放 | 否 |

**关键规则：**
- `required` 中任何一项被拒 → 不可安装（沿用现有 `Evaluate()` 语义）。
- 版本升级时，若 `required` 能力集扩大或约束放宽 → 强制重新授权（现有 `_validate_manifest_upgrade_compatibility` 已覆盖，需扩展到 constraints 维度）。
- T2/T3 能力的调用必须写入审计日志，且日志包含 capability、参数指纹（不含敏感值）、结果、耗时。

### 4.4 唯一通路（Sole Path）的强制手段

「插件一切操作只能通过框架暴露的接口」需要技术手段保证，而非仅靠约定：

1. **协议白名单**：`PluginHostBroker` 仅注册 9 个方法，其余返回 `-32601`。新增方法必须走 ADR。
2. **Schema 双向校验**：请求体按命令签名 schema 过滤未声明字段（`PrepareCommandInput` 已实现）；**补充响应体校验**。
3. **参数转译**：所有资源标识使用宿主生成的 opaque handle（`file_ref` 范式），禁止传递真实路径、URL、连接串。
4. **OS 面收敛**：L1 确保插件进程即使绕过协议层自行 syscall，也拿不到文件、网络、注册表、进程创建能力。
5. **静态扫描兜底**：`static_review.py` 的 `PD-STATIC-001~006` 检测插件二进制中的敏感 API 引用，作为编译期告警。

### 4.5 显式拒绝清单（Deny List）

以下能力**桌面宿主永不提供转译路径**，且应在 manifest 校验阶段直接拒绝（而非运行时拒绝）：

`process:spawn` · `network:listen` · `registry:write` · `credential:read` · `system:persistence` · `system:driver` · `ui:global_hook` · `memory:read_other_process`

当前 `KnownCapabilities` 已列出其中大部分但标注为「可声明、本地不授予」。重构后应改为：**声明即拒绝（declare-to-reject）**，避免开发者误以为声明后可通过审核。

> 注：`network:internet` **不列入永久拒绝清单**（决策 2026-09-01：不对第三方永久关闭）。其默认不授予，第三方需经 **T3 特批流程**（管理端 A-G4，绑定开发者信誉与安全评审）方可获得；授予后仍需接受更密集的动态 canary 探测（§5.3）与运行时监控（A-M2）。`net:fetch:allowlist`（白名单域名代发）仍作为更安全的默认替代，优先于直接授予 `network:internet`。

### 4.6 宿主自我降权（新增 L0）

当前宿主持有用户完整权限，一旦宿主被攻破（如通过恶意插件返回的畸形数据触发宿主反序列化漏洞），用户环境即失守。建议：

1. **宿主拆分为两个进程**：
   - `Host.UI`（中等完整性，负责窗口、市场、用户交互）
   - `Host.Sandbox`（负责插件进程创建、管道管理、Broker，以**更低完整性级别**运行）
   - 二者通过命名管道 + ACL 通信，`Host.Sandbox` 仅持有插件相关目录权限。
2. 宿主启动时做**完整性自检**：校验自身二进制签名、Broker 方法白名单哈希、策略文件哈希，任一不符即进入安全模式。
3. `ProtectedSessionStore` 中的令牌仅在 `Host.UI` 进程内解密，`Host.Sandbox` 只接收短期 scope token。

## 5. 三端职责划分

### 5.1 总览

| 端 | 定位 | 核心职责 | 明确不做 |
|---|---|---|---|
| **桌面宿主端** | 执行与隔离 | 进程沙箱、能力代理、UI 渲染、本地存储、安装/升级/回滚、撤销同步、审计上报 | 不做审核决策、不做身份签发、不做业务逻辑 |
| **Web 开发者端** | 供给与身份 | 开发者入驻、Ed25519 密钥登记、项目与版本管理、`.pdpkg` 上传、源码/provenance 提交、审核进度查看 | 不做安全判定、不接触平台签名私钥 |
| **Web 插件管理端** | 审核与治理 | 静态/动态审核流水线调度、人工审核台、发布通道（canary/stable）、撤销、举报处置、Runner 编排与监控、策略版本管理 | 不做插件运行时、不持有开发者私钥 |
| **API（共享内核）** | 事实来源 | 插件目录、版本、审批状态、授权绑定、撤销表、审计存储、平台签章 | — |

### 5.2 桌面宿主端（C# / .NET）

**模块边界（重构目标态）：**

```
PasswordDetective.Desktop
├── Host.UI            (WPF，用户交互层)
├── Host.Sandbox       (低权限进程，插件生命周期)
├── Pdpp.Sandbox.Core  (★ 独立组件，被 Host.Sandbox 与 Review Runner 共用)
│   ├── Process/       AppContainer · JobObject · ACL · 环境净化 · 句柄白名单
│   ├── Protocol/      JSON-RPC 编解码 · 双向 Schema 校验 · 限流
│   └── Broker/        capability · 参数约束 · 配额 · 审计
├── Pdpp.Packages      .pdpkg 校验 · 双签名 · 安装 · 迁移 · 回滚
└── Pdpp.Registry      本地安装账本 · 授权快照 · 撤销缓存
```

**关键重构动作：**
- 将 `WindowsSandboxedProcess.cs` 抽象为 `ISandboxedProcessFactory`，**仅 Windows 实现**（`Pdpp.Sandbox.Core` 的 Rust 内核仅针对 Windows 目标编译）。决策（2026-09-01）确认不立项 macOS / Linux，不在接口层预留跨平台占位分支。
- 引入 `CsWin32` 替代手写 P/Invoke，降低维护成本与签名错误风险。
- Broker 能力面扩展（§5.5）。

### 5.3 Web 插件管理端（Admin）

**审核流水线目标态（修复 D2 盲区）：**

```
上传 → [S1 静态+供应链] → [S2 动态行为] → [S3 人工] → 发布
                              ↑
                     Runner 池（独立 VM / 隔离网络）
```

**S2 动态审核必须改造**：当前 canary 依赖插件主动声明命令。改为**宿主侧强制注入探测**，不依赖插件配合：

| 探测项 | 强制方式 | 判定 |
|---|---|---|
| 沙箱有效性 | 宿主启动后 `GetTokenInformation(TokenIsAppContainer)` 断言 | critical，失败即拒 |
| 环境泄漏 | 注入伪装变量 `PD_CANARY_SECRET`，扫描插件输出与网络载荷 | critical |
| 文件越权 | 在沙箱外预置 canary 文件，枚举尝试读取 | critical |
| 网络出站 | 预置本地 HTTP 监听，插件任何出站尝试均被 WFP 记录 | critical |
| 子派生 | Job Object 计数 + `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` | critical |
| 超时终止 | 强制执行 `hang` 命令（宿主直接发送，不需插件声明） | critical |
| 超大响应 | 宿主主动请求返回 >1MB 的响应，验证截断 | major |

**其余职责补齐：**
- Runner 部署到独立 VM + 隔离网络（当前文档自陈未验证）。
- `review_policy.py` 纳入版本化管理，每次策略变更产生 `policy_version` 并留存。
- 平台签名密钥强制 `openbao_transit`（D5），启动时配置门禁：生产环境若为派生模式直接拒绝启动。

### 5.4 Web 开发者端（Web）

- 保持现有功能（项目/密钥/版本/上传/审核进度）。
- **新增：能力声明向导**——开发者勾选能力时，前端实时展示该能力所属 Tier、需要的审核材料、用户侧将看到的授权提示，并调用服务端 `/capabilities/precheck` 预校验（避免提交后才被拒）。

- **新增：多语言 SDK 下载**（回应 D7）：至少补齐 Go、Rust、Python 三份 SDK，由 conformance 测试保证行为一致。

### 5.5 Broker 能力面扩展（回应「尽可能宽松」诉求）

## 6. 桌面端技术选型对比

### 6.1 约束条件推导（这是选型的全部依据）

由于插件是独立进程、通过 stdio JSON-RPC 通信，**宿主语言的决定因素收敛为四项**：

| 约束 | 权重 | 说明 |
|---|---|---|
| **C1 Windows 安全 API 可达性** | 决定性 | 宿主必须调用：`CreateAppContainerProfile`、`CreateProcessAsUser` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`、`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`、`SetHandleInformation`、`GetTokenInformation`、`CreateJobObject`/`SetInformationJobObject`（含 `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP`）、ACL/SD 操作、`CreateEnvironmentBlock`、`TerminateJobObject` |
| **C2 桌面 UI 能力** | 高 | 需承载主窗口、插件市场、命令表单、主题系统 |
| **C3 存量资产复用** | 高 | 约 1.1 万行已验证的 Windows 安全代码 + 60 个源文件 |
| **C4 分发与体积** | 中 | 桌面客户端需自更新、需考虑 Win10/Win11 兼容 |

**明确不构成约束的因素**：插件语言自由度（已由进程隔离保证）、插件执行性能（各插件独立进程，与宿主无关）。

### 6.2 候选对比矩阵

| 方案 | C1 安全 API | C2 UI | C3 复用 | C4 分发 | 跨平台 | 综合 |
|---|---|---|---|---|---|---|
| **A. C#/.NET + WPF**（现状） | ★★★★★ 已全部实现并验证 | ★★★★☆ 成熟、原生观感 | ★★★★★ 100% | ★★★☆☆ 需 .NET 运行时 | ✗ | **推荐** |
| **B. C#/.NET + WinUI 3** | ★★★★★ | ★★★★☆ 现代但需 WASDK 运行时 | ★★★★☆ UI 层重写 | ★★★☆☆ | ✗ | 可选（UI 现代化） |
| **C. C#/.NET + Avalonia** | ★★★★★ P/Invoke 不受影响 | ★★★☆☆ 自绘，原生感略逊 | ★★★★☆ UI 层重写 | ★★★★☆ | ✓ | 仅当强跨平台需求 |
| **D. Rust + Tauri 2** | ★★★★☆ `windows-rs` 覆盖好，但需重写 | ★★★☆☆ WebView2 + Web 栈 | ☆ 全部重写 | ★★★★★ 体积小 | ✓ | 高成本高收益，见 §6.4 |
| **E. C++ / Qt** | ★★★★★ 原生 | ★★★★★ | ☆ 全部重写 | ★★★★☆ | ✓ | 内存安全靠人，不推荐 |

| **G. Electron / Node** | ★☆☆☆☆ 需 C++ addon；且宿主自带 V8 巨大攻击面 | ★★★★☆ | ☆ | ★★☆☆☆ 体积大 | ✓ | **明确排除** |

### 6.3 逐项说明

**A. C#/.NET + WPF（现状，推荐保留）**
- 优势：C1 满分——所有 Windows 安全 API 已实现并通过 conformance 与动态审核双重验证；C3 满分。
- 劣势：Windows-only。但注意，项目代码中已存在 `OperatingSystem.IsWindows()` 判断，说明作者已有平台意识；且沙箱机制本身（AppContainer）是 Windows 独有的，跨平台需要完全不同的实现（macOS seatbelt / Linux namespaces+seccomp），这不是换语言能解决的。
- 重构动作：引入 `CsWin32` 生成 P/Invoke 绑定、抽出 `ISandboxedProcessFactory` 接口。

**B. WinUI 3 / WindowsAppSDK**
- 若目标是 UI 现代化，这是同语言内的最小代价路径。但 WASDK 的部署与版本碎片化成本需评估，且当前无强诉求。建议列为可选项而非必做。

**C. Avalonia**
- 唯一价值是跨平台 UI。但本项目沙箱层是 Windows 专有的，换 Avalonia 只解决 UI 跨平台，不解决沙箱跨平台，**收益不完整**。**决策（2026-09-01）：本次不立项 macOS / Linux 桌面端，Avalonia 不采用。** 保留 `ISandboxedProcessFactory` 接口作为纯防御性抽象，不实现跨平台分支。

**D. Rust 实现 `Pdpp.Sandbox.Core`（已立项，限定范围）**
- 范围澄清：**不是用 Tauri+Rust 重写整个桌面端**，而是仅把「沙箱内核」（`Pdpp.Sandbox.Core`）用 Rust 实现为可被宿主调用的独立组件；桌面端 UI 与宿主逻辑仍保持 C#/.NET + WPF。
- 优势：`windows-rs` 由 Microsoft 官方维护，AppContainer/Job Object/ACL 覆盖良好；内存安全对安全关键路径（进程创建、句柄、ACL）有实质价值；产物体积小；**可被桌面宿主与审核 Runner 共用同一份二进制**（P6，消除当前 Runner 复用桌面代码导致的耦合）。
- 劣势：需引入 Rust 工具链与 FFI/IPC 边界；团队需具备 Rust 能力；C# 侧原 `WindowsSandboxedProcess.cs` 的 1047 行逻辑需逐条迁移并通过 conformance 双验证。
- 调用方式（决策 2026-09-01）：Rust 内核编译为**独立可执行文件**，宿主 `Host.Sandbox` 进程通过命名管道（IPC）+ JSON 指令调用其能力（创建 AppContainer、起受控子进程、管 Job Object、设 ACL、环境净化、canary 探测）；**不采用 `cdylib` + FFI**。独立进程边界更清晰，内核崩溃不影响宿主，且同一二进制可被审核 Runner 直接复用。接口契约见 §6.5。
- 立项依据：决策（2026-09-01）确认立项，纳入 P2 接口抽象、P3 实现替换。

**F/G/H/I 不推荐的共同原因**：C1 不达标。用 Electron 做安全沙箱宿主尤其本末倒置——引入一个数十 MB 的脚本引擎作为可信计算基（TCB），攻击面不降反升。

### 6.4 选型建议（分场景决策）

| 场景 | 建议 |
|---|---|
| 维持 Windows 单一平台（当前，已确认） | **A. C#/.NET + WPF** 做 UI 与宿主，**D. Rust** 做沙箱内核，混合架构 |
| 需要 UI 现代化 | A + 局部升级到 Fluent 风格（WPF 不引入 WASDK） |
| 安全内核最高等级保障 / 内核被多端复用 | **A + D 混合（已立项）**：C# 宿主 UI 不变，Rust 实现 `Pdpp.Sandbox.Core`，桌面与 Runner 共用 |

> 决策（2026-09-01）：不立项 macOS / Linux；`ui:panel` 采用 JSON Schema 式声明；`Pdpp.Sandbox.Core` 的 Rust 实现正式立项（仅内核，非桌面端整体重写）。

**一句话结论：桌面端保留 C#/WPF 作为 UI 与宿主外壳；沙箱内核抽成独立、可复用、接口化的 Rust 组件（`Pdpp.Sandbox.Core`），宿主经 IPC 调用——既不放弃 C# 存量资产，又让安全关键路径获得内存安全保障与被多端复用的能力。**

### 6.5 `Pdpp.Sandbox.Core` 接口契约（Rust 内核）

宿主（`Host.Sandbox`，C#，低完整性进程）与 Rust 内核之间以「请求/响应」JSON 指令通信，内核是唯一拥有 Windows 安全 API 调用的执行体。

| 指令组 | 方法 | 输入（关键字段） | 输出 |
|---|---|---|---|
| 沙箱 | `sandbox.create` | `plugin_id`, `limits{memory_mb,cpu_percent,command_timeout_seconds}` | `profile_sid`, `work_dir`, `acl_handle` |
| 沙箱 | `sandbox.destroy` | `profile_sid` | `ok` / 残留清理状态 |
| 进程 | `process.spawn` | `profile_sid`, `entrypoint`, `stdin/stdout/stderr_handle`（仅 3 管道） | `pid`, `job_handle` |
| 进程 | `process.terminate` | `pid` / `job_handle`, `reason` | `ok` |
| 资源 | `fs.grant_read` | `plugin_id`, `real_path`, `max_bytes` | `file_ref`（32 位 hex） |
| 资源 | `fs.read_chunk` | `file_ref`, `offset`, `length` | `bytes`（≤512KB 分块） |
| 资源 | `fs.grant_write` | `plugin_id`, `real_path` | `file_ref`（写入经宿主代写） |
| 环境 | `env.sanitize` | `host_secret_keys[]` | 净化后的环境块（白名单变量 + 重定向 APPDATA/LOCALAPPDATA/TEMP/USERPROFILE/HOMEPATH） |
| 网络 | `net.block_outbound` | `appcontainer_sid` | WFP 规则句柄（显式阻断，D1） |
| 注册表 | `reg.deny_write` | `appcontainer_sid` | ACL 句柄（显式拒绝，D1） |
| 探测 | `canary.run` | `plugin_id`, `task`（强制注入：`probe`/`environment`/`spawn-child`/`hang`/`oversized-output`） | 逐探针 `passed`/`evidence` |
| 自检 | `attest.host` | — | `is_appcontainer`、`no_host_secret_leak`、`no_fs_breakout` 断言结果 |

契约要点：
- **内核是唯一 syscall 门**（P1 单一通路），宿主不得自行调用 Windows 安全 API。
- 所有资源标识使用内核签发的 `file_ref`，插件进程看不到真实路径（§4.1 范式）。
- `canary.run` 由内核强制注入命令，不依赖插件 manifest 声明（修复 D2）。
- 指令体强制双向 JSON Schema 校验，消息 ≤1MB、深度 ≤32、超时即终止。

## 8. 风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| 抽出 `Pdpp.Sandbox.Core` 期间引入回归 | 高 | conformance 测试先行；保持双实现并行一个版本 |
| 宿主双进程拆分增加 IPC 复杂度与延迟 | 中 | 仅 `Host.Sandbox` 处理插件 I/O，UI 路径不经过 IPC |
| 能力四元组破坏现有 4 个官方插件 | 中 | v1 manifest 自动降级为「无约束」，P2 阶段内完成官方插件迁移 |
| WFP 规则与用户现有防火墙策略冲突 | 中 | 规则按插件 SID 精确作用域，提供卸载清理 |
| Rust 沙箱内核迁移成本超预期 / FFI 边界 Bug | 中 | 契约级测试先行；C# 旧实现保留一个版本并行灰度，失败可回退 |
| 审核流水线部署到隔离网络后反馈周期变长 | 低 | 本地 `pdpp-lint` 前置拦截大部分问题 |

## 9. 决策记录（2026-09-01 已确认）

| # | 事项 | 决策 | 影响 |
|---|---|---|---|
| 1 | macOS / Linux 桌面端 | **不立项**，仅 Windows | 移除 Avalonia 选项；沙箱实现仅 Windows，不预留跨平台分支（`ISandboxedProcessFactory` 仅 Windows 实现） |
| 2 | `ui:panel` UI 描述格式 | **JSON Schema 式声明** | 宿主渲染声明式 UI，替代插件自创 WPF 窗口（D9）；PDPP v1.1 提案 |
| 3 | `Pdpp.Sandbox.Core` 的 Rust 实现 | **立项**（限定范围：仅内核，非桌面端整体 Tauri 重写） | 桌面 UI/宿主仍 C#/WPF；Rust 内核经 IPC 被宿主与 Runner 共用；见 §6.5 接口契约 |
| 4 | T3 能力 `network:internet` 是否对第三方永久关闭 | **不永久关闭**，默认不授予，经 T3 特批可授予 | 第三方开放需更强动态 canary + 运行时监控；见 §4.3 / §4.5 / §12 A-G4 |
| 5 | `ui:panel` 的 JSON Schema 子集边界 | **宽松**，支持宿主主题变量注入 | 宿主侧组件库较全，插件 UI 体验接近原生；见 §5.5 |
| 6 | Rust 内核交付形态 | **独立可执行文件（IPC）**，不采用 cdylib / FFI | 内核崩溃隔离，二进制可被 Runner 复用；见 §6.5 |
