# 密码侦探社项目规格说明书 v3.0

**文档状态：** 开发基线  
**基线日期：** 2026-08-01  
**适用范围：** Web 用户端、管理端、Windows 桌面端、后端 API 与基础设施  
**替代文档：** 原项目文档仅作为需求来源；冲突项以本说明书为准

## 1. 执行摘要

密码侦探社定位为“授权压缩包密码恢复与社区验证平台”。用户在本地计算压缩包文件指纹，通过指纹查询社区已收录的解压密码；也可在确认自己有权处理该文件的前提下，贡献已经本地验证成功的“文件指纹—解压密码”记录。

本版本将项目从宽泛的“密码哈希反查平台”收敛为可实现、可审计、可合法运营的产品：统一数据语义，修复桌面端信任模型，缩小 MVP 范围，建立候选密码状态机、证据链、权限与审计机制，并明确可量化的性能、安全和发布标准。

### 1.1 MVP 成功标准

- 用户无需上传压缩包，即可在浏览器或桌面端本地计算指纹。
- 精确查询在正常负载下 P95 响应时间不高于 500 ms（不含客户端网络）。
- 已验证数据可被查询和复制；待验证数据默认不向匿名用户公开完整密码。
- 桌面端成功解压后可提交可校验的验证回执，但客户端回执不被视为绝对可信。
- 所有密码揭示、贡献、验证、状态变更和管理员操作均可追溯。
- 发布前不存在 P0/P1 缺陷，高危安全问题全部关闭或有书面风险接受记录。

## 2. 产品定位与合规边界

### 2.1 允许的使用场景

- 恢复本人创建、本人拥有或已获明确授权处理的 ZIP、7z、RAR 等压缩包密码。
- 对已经合法获得的压缩包，在本地进行文件指纹计算和解压验证。
- 分享不包含个人信息、商业秘密、恶意内容或侵权内容的解压密码记录。
- 安全研究、数字取证或运维恢复场景中，经组织授权后的内部使用。

### 2.2 禁止的使用场景

- 查询、导入、交易或导出网站账号口令、撞库字典、泄露凭据或彩虹表。
- 未经授权破解、传播或访问第三方压缩包内容。
- 自动抓取 Have I Been Pwned、CrackStation、RockYou 等泄露口令数据并转为明文服务。
- 提供密码猜测、暴力破解编排、Hashcat 字典导出、AI 猜密或规避访问控制能力。
- 公开展示可识别个人、组织或案件的信息，如完整本地路径、客户名称或敏感文件名。

### 2.3 产品内强制措施

- 注册、贡献和桌面端首次使用时展示授权声明并记录版本与同意时间。
- 贡献页面提供内容规范和举报入口；管理员可隔离、下架和删除记录。
- 默认不接收压缩包实体；后端仅接收指纹、候选密码和最小化验证元数据。
- 数据导出、批量揭示和反向明文检索不进入 MVP。

## 3. 核心概念统一

### 3.1 正确的数据语义

- **压缩包文件指纹（archive fingerprint）**：对整个压缩包文件字节计算的 MD5、SHA-1、SHA-256 或 SHA-512 摘要，用于识别“同一个文件”。
- **解压密码（archive password）**：用户用于打开压缩包的字符串。
- **候选密码（password candidate）**：某个压缩包记录下的一条密码候选，可能处于待验证、已验证、已拒绝或隔离状态。
- **验证回执（verification receipt）**：客户端完成本地解压测试后产生的结构化证据，包含文件指纹、候选密码摘要、结果、客户端版本、挑战随机数、时间戳和签名。

压缩包文件指纹与解压密码之间不存在 `hash(password) == archive_fingerprint` 的关系。后端不能通过对密码做 MD5/SHA 计算来证明密码能解压文件；正确性必须来自本地解压结果、独立反馈或管理员复核。

### 3.2 指纹策略

- 新提交默认同时计算 SHA-256 和 MD5；SHA-256 作为主指纹，MD5 用于兼容历史数据。
- 支持用 MD5、SHA-1、SHA-256、SHA-512 任一完整指纹精确查询；统一转为小写十六进制。
- 不做部分哈希、通配符或模糊查询，避免枚举和误命中。
- 同一压缩包可关联多个算法指纹，由 `archive_fingerprints` 表统一管理。

## 4. 用户与角色

| 角色 | 核心能力 | 限制 |
|---|---|---|
| 匿名访客 | 指纹格式校验、查看是否有匹配、查看公开统计 | 不揭示完整密码，不贡献，不投票 |
| 注册用户 | 查询与揭示、贡献记录、反馈验证结果、查看个人历史 | 受配额、信誉分和风控限制 |
| 可信贡献者 | 较高配额、较高反馈权重、批量贡献申请 | 权限由规则授予，可撤销 |
| 内容审核员 | 审核、隔离、合并重复记录、处理举报 | 无系统配置和账号权限管理能力 |
| 系统管理员 | 用户、角色、配置、审计、告警与发布管理 | 高风险操作必须二次验证并记录审计日志 |
| 服务账号 | 执行任务、通知和维护作业 | 最小权限，无交互登录 |

## 5. 范围与优先级

### 5.1 MVP（必须交付）

1. 用户注册、登录、刷新令牌、退出和密码重置。
2. 浏览器本地文件指纹计算，不上传文件内容。
3. 按完整指纹精确查询，结果遮挡、揭示、复制和配额扣减。
4. 单条贡献、重复检测、候选密码状态管理。
5. Windows 桌面端选择压缩包、计算指纹、测试密码、提交验证回执，并从后端稳定通道检查升级。
6. 社区成功/失败反馈、防重复反馈和基础信誉分。
7. 用户中心：贡献、反馈、积分/信誉事件、登录会话。
8. 管理端：数据审核、举报、用户处置、配置、审计日志和基础仪表盘。
9. Redis 限流、异步通知、结构化日志、指标、备份与恢复演练。
10. 自动化测试、CI、容器化开发环境和生产部署说明。

### 5.2 MVP 后第一阶段

- CSV 批量贡献与异步任务进度。
- 可信贡献者申请与审核。
- 更完整的数据质量报表、通知中心和运营统计。
- 桌面端静默安装、分批发布、回滚编排与正式证书签名流水线。
- 对象存储中的脱敏任务报告。

### 5.3 暂不实施

论坛、积分商城、实物兑换、悬赏破解、公开 API 市场、浏览器插件、移动 App、社交关系、广告、公开数据集爬虫、明文反查、模糊搜索、AI 猜密、密码字典生成与 Hashcat 集成。上述功能必须单独完成法律、安全、隐私和商业评审后才能立项。

## 6. 功能需求

### 6.1 认证与账号

- **AUTH-01** 支持邮箱或用户名注册；用户名唯一，邮箱验证策略可配置。
- **AUTH-02** 登录成功返回短期访问令牌和可轮换刷新令牌；刷新令牌只以哈希形式存储。
- **AUTH-03** 支持退出当前会话、退出全部会话、查看并撤销登录设备。
- **AUTH-04** 管理员与高风险操作强制二次验证；用户密码修改、TOTP 停用和账号删除申请必须使用当前密码再认证，启用 TOTP 时还必须提供动态码，并由服务端签发默认 5 分钟有效、绑定当前会话族与精确操作目的的一次性凭据；凭据仅保存摘要且不得重放。
- **AUTH-05** 登录失败达到阈值后采用渐进延迟和临时锁定，并记录风控事件。
- **AUTH-06** 账号密码使用 Argon2id；仅在兼容环境不满足时使用 bcrypt。

### 6.2 本地指纹计算

- **HASH-01** Web 端使用分块读取计算 SHA-256 和 MD5，全程不上传文件。
- **HASH-02** 展示文件名、大小、进度、计算耗时和结果；取消操作后释放资源。
- **HASH-03** 默认最大文件建议值由配置控制；大文件必须流式处理，不一次性读入内存。
- **HASH-04** 手动输入时自动识别算法并严格校验长度与十六进制字符。

### 6.3 查询与密码揭示

- **SEARCH-01** 仅支持完整指纹精确查询。
- **SEARCH-02** 匿名用户只看到“有/无匹配”、状态和脱敏元数据；注册用户在配额允许时揭示完整密码。
- **SEARCH-03** 结果按状态、证据强度、最近有效验证时间排序，不按查询次数自动提升可信度。
- **SEARCH-04** 同一压缩包存在多个候选时全部展示，但默认突出最高可信候选。
- **SEARCH-05** 每次揭示生成审计事件；日志不得写入明文密码、访问令牌或完整文件名列表。
- **SEARCH-06** 无结果时引导本地验证和贡献，不提供暴力破解建议。

### 6.4 数据贡献

- **SUB-01** 贡献必须包含至少一个完整文件指纹和非空解压密码。
- **SUB-02** 用户确认授权声明；后端记录声明版本、时间和来源。
- **SUB-03** 同一压缩包、同一密码候选重复提交时合并为新的证据事件，不创建重复候选。
- **SUB-04** Web 手工提交默认为 `pending`；桌面端成功回执提高证据分，但仍需满足状态机规则。
- **SUB-05** 文件名元数据默认关闭；启用时仅允许基本文件名、最多 20 个、单项最长 120 字符，移除路径和控制字符。
- **SUB-06** 贡献成功只发放“待结算积分”；候选成为 `verified` 后才正式入账。

### 6.5 本地验证与桌面端

- **DESK-01** MVP 桌面端为 Windows WPF 应用，目标运行时为 .NET 10 LTS，并在发布时固定到最新受支持补丁。
- **DESK-02** 支持 ZIP 和 7z；RAR 作为兼容性验证后的可选项，不承诺首版覆盖全部加密变体。
- **DESK-03** 验证过程只在本地读取压缩包；后端不接收压缩包实体或解压出的文件内容。
- **DESK-04** 首次启动生成安装实例密钥，私钥使用 Windows DPAPI 保护；使用随机安装 ID，不采集主板序列号、MAC 地址等硬件标识。
- **DESK-05** 提交前向服务端申请一次性挑战；回执签名覆盖挑战、指纹、候选密码摘要、验证结果、客户端版本和时间戳。
- **DESK-06** 服务端验证签名、防重放和时钟窗口，并结合账号信誉、安装历史、速率和异常模式计算证据权重。
- **DESK-07** 固定 `User-Agent` 只用于观测，不作为信任凭据。
- **DESK-08** 客户端可被逆向，因此任何客户端证明都不能直接绕过服务端风控或自动获得最高可信状态。
- **DESK-09** 后端按通道、平台和架构维护不可变版本发布记录；检查更新时返回最高已发布版本、最低受支持版本、强制升级标记、发布说明和制品完整性元数据。
- **DESK-10** 发布管理员必须通过 RBAC 与当前会话 MFA 才能创建、上传、发布或撤回桌面版本；制品上传按声明的字节数和 SHA-256 流式校验并写入审计日志。
- **DESK-11** 匿名客户端只能检查更新和下载仍处于 `published` 状态的制品；撤回版本立即停止下载，下载响应提供不可变缓存、ETag 和标准摘要头。
- **DESK-12** 桌面端启动后自动检查稳定通道，并提供用户主动触发的系统浏览器下载入口；首版不静默下载、不自动执行安装包。生产发布门禁要求发布记录标记为已完成代码签名验证，但客户端安装前仍应核验操作系统展示的签名者。
- **DESK-13** 管理端提供受 MFA 保护的桌面发布工作流：创建不可变草稿元数据、上传或重试制品、复核摘要与签名记录、显式确认发布或撤回；浏览器只校验输入格式、文件名与大小，后端仍是制品 SHA-256 和生命周期门禁的最终执行者。

### 6.6 社区反馈与状态机

候选密码状态统一为：

`pending → verified`、`pending → rejected`、`verified → quarantined → verified/rejected`。

- **VERIFY-01** 同一账号对同一候选只能保留一个有效反馈；修改反馈需记录历史。
- **VERIFY-02** 同一安装实例、IP 网段和异常关联账号的反馈进行去重或降权。
- **VERIFY-03** 单次桌面成功回执不直接产生 `verified`；默认规则为“两个相互独立的有效成功证据，且加权失败证据低于阈值”。
- **VERIFY-04** 三个独立有效失败证据或短时失败激增时进入 `quarantined`，暂停密码揭示并触发审核。
- **VERIFY-05** `verified` 后出现高可信失败证据可降级；任何自动状态变更写入 `record_state_events`。
- **VERIFY-06** 查询命中数只用于热度统计，不能作为正确性证据。
- **VERIFY-07** 阈值由版本化规则配置，不允许管理员无审计地直接修改历史证据。

### 6.7 积分与信誉

- 积分是可消费激励；信誉分是风控信号，两者分账、分表、不可互相直接兑换。
- 初始信誉分统一为 50，范围 0–100；等级由累计有效贡献和活跃度计算，不直接等于信誉分。
- 有效候选首次变为 `verified` 时向首位贡献者和有效验证者结算积分；重复贡献不重复奖励。
- 误报、恶意提交、关联账号刷票按规则扣减信誉；重大异常进入人工复核。
- 所有积分和信誉变化采用不可变事件流水，禁止直接覆盖余额而不留原因。

### 6.8 用户中心

- 个人资料、密码修改、TOTP、会话和授权声明记录；密码修改、TOTP 停用和账号删除申请统一经过短时一次性再认证。
- 查询揭示记录（仅显示指纹摘要，不回显已删除密码）。
- 贡献记录、候选状态、证据数量、积分结算状态。
- 反馈历史、信誉事件、申诉入口。
- 数据导出和账号删除申请；删除流程需处理审计保留与法定义务。

### 6.9 管理端

MVP 菜单按优先级收敛为：

1. 仪表盘：查询量、命中率、贡献量、验证率、隔离量、错误率、队列积压。
2. 数据审核：候选列表、证据详情、状态时间线、合并、隔离、恢复、删除。
3. 举报与申诉：内容举报、账号申诉、处理时限和结果通知。
4. 用户与权限：用户状态、信誉事件、角色与最小权限。
5. 安全与风控：限流、登录策略、TOTP、异常规则、封禁策略。
6. 系统配置：站点基础信息、功能开关、配额和验证规则版本。
7. 桌面发布：版本草稿、制品上传、摘要/签名记录复核、发布和撤回。
8. 审计与日志：管理员操作、认证事件、敏感数据访问、导出。
9. 运维监控：服务健康、任务队列、数据库、缓存、告警联系人。

仪表盘首版口径：

- 查询量统计通过指纹格式校验的有效档案查询；命中率为返回可见候选档案的查询数除以有效查询数。查询遥测不得保存完整指纹。
- 贡献量按选定时间窗口内新增贡献记录统计；验证率为当前已验证候选数除以候选总数；隔离量为当前隔离候选快照。
- 错误率首版采用已审计业务操作中非成功结果占比，并在界面明确其不等同于全量 HTTP 请求错误率。全量请求错误率由后续可观测性指标负责。
- 队列积压至少包含待审核候选、处理中举报/申诉、未关闭风险告警、待处理隐私导出和账号删除申请。
- 指标必须返回观察窗口和生成时间；无历史遥测时不得伪造或回填演示数据。

爬虫、论坛、商城、悬赏和广告设置从 MVP 菜单移除。

M4 首个人工审核切片采用以下约束：

- 候选审核列表支持按 `pending/verified/quarantined/rejected` 状态、候选 ID、存档 ID 或完整/部分指纹摘要筛选；该模糊能力仅存在于 MFA 管理端，不改变公开查询必须使用完整指纹的规则。
- 审核详情仅返回候选/存档标识、指纹、证据聚合、证据修订和状态时间线；不得返回候选密码明文、密文、nonce、密钥版本或去重标签。
- 人工状态转换使用版本化规则 `moderation-v1`，必须携带受控原因码和 `Idempotency-Key`，并记录操作者、前后状态、`request_id`、原因说明及当时证据快照。
- 人工处置允许的状态转换为：`pending → verified/quarantined/rejected`、`verified → quarantined/rejected`、`quarantined → pending/verified/rejected`、`rejected → pending`；禁止同状态空操作。
- 审计日志只记录原因码、前后状态和状态事件 ID，不复制自由文本原因说明或任何候选秘密。

M4 第 2 个举报/申诉切片采用统一信任案件模型：

- 案件类型支持 `report`、`appeal` 和 `account_appeal`，案件主体统一标识为 `candidate/account/risk_alert`，且每个案件只能关联一种主体；状态固定为 `open → in_review → resolved/dismissed`，已关闭案件只能通过专用重开命令和受控原因重新进入 `open`，禁止同状态空操作。
- 登录用户可举报任意存在的候选；贡献申诉仅允许该候选的贡献者针对 `rejected` 或 `quarantined` 状态发起，说明必填。账号申诉只允许为当前登录账号提交，目标账号由服务端派生，不接受客户端指定；必须使用受控原因码、期望恢复动作和最多 1000 字符的最小披露证据摘要。可选关联案件必须指向同一候选。
- 用户只能分页查看本人提交的案件，并可通过 `/trust/cases/{case_id}` 查看本人案件详情和不可变时间线；非所有者统一返回不存在。审核员/管理员必须在 MFA 会话中查看统一队列、详情和不可变事件时间线，不得通过用户接口读取其他人的案件。
- 举报、贡献申诉、账号申诉和管理写操作均要求 `Idempotency-Key`、端点限流和请求号；重复同载荷返回既有结果，不同载荷复用同一键返回冲突。
- 管理案件状态写操作必须携带 `expected_version`。`assign` 只允许把 `open/in_review` 案件指派给启用状态的审核员/管理员；`reopen` 只允许把 `resolved/dismissed` 案件重开为 `open`，并清理当前负责人和结论元数据。版本冲突统一返回 `409 trust.case_version_conflict`，事件保存负责人前后值；审计日志只记录原因码、结构化前后值、版本和事件 ID，不复制自由文本。
- 当前 WP2 第 2 轮已实现独立 `assign`/`reopen` 和通用 `transition` 的乐观并发门禁；账号/候选关联处置、奖励/信誉补偿、结果通知 Outbox 和最终 `resolve` 原子编排仍待后续轮次。案件处理结论与候选状态修改保持分离，未完成原子处置前不得由前端拼接多个无事务写接口。

M4 第 3 个积分与信誉切片采用以下约束：

- 新用户信誉初始值为 50，范围固定为 0～100；积分余额与信誉分保持分账。
- `points_ledger` 是积分事实来源，可用、待结算和已冲正金额均由流水投影，不维护无事件的第二份可变余额。
- `reputation_events` 保存每次实际信誉变化的前后分值、受控原因码、规则版本和引用对象；`users.reputation_score` 仅作为读取投影。
- `reputation-v1` 在候选首次成为 `verified` 时向首位贡献者增加 3 分、向当时有效成功验证者增加 2 分；引用唯一约束和用户行锁保证重复请求不重复加分。
- 用户只能读取本人积分汇总、积分流水、信誉事件、贡献和反馈统计；Web 不接受目标用户 ID，也不显示候选秘密。
- 已验证候选后续被隔离或拒绝时，必须通过新的补偿规则追加积分/信誉事件，不得删除或改写原始奖励事件。
- `reward-compensation-v1` 将首次贡献者和原始成功验证者的目标净奖励定义为：目标状态为 `verified` 时保留原始实际奖励，目标状态为 `pending/quarantined/rejected` 时归零。
- 隔离/拒绝后恢复为 `verified` 时只恢复已经存在的原始奖励来源；首次验证后新增的证据不得通过恢复流程获得追溯奖励。
- 每次校正必须绑定不可变状态事件、用户、奖励类型和原始来源引用，与状态转换在同一事务内追加积分流水、信誉事件和校正事件；重复请求不得重复校正。
- 信誉校正保存 0～100 边界裁剪后的实际变化量，因此积分和信誉的恢复值可能因用户后续信誉变化而不同。

M4 第 5 个失败激增风险告警切片采用以下约束：

- `risk-alert-v1` 观察当前有效失败反馈：15 分钟内至少 3 个按“安装实例 → IP 网段 → 账号”优先级去重后的独立失败组，且失败权重不低于 3.0 时，创建 `failure_surge/high` 告警。
- 告警检测与反馈证据、自动候选状态变化和奖励校正在同一数据库事务内完成；任一步失败不得留下部分结果。
- 同一候选、告警类型和规则版本最多存在一个 `open` 或 `acknowledged` 活跃告警；已解决后出现新的材料变化和新一轮激增时可创建新告警。
- 告警只保存候选/触发证据标识、规则版本、观察窗口、独立失败数和聚合权重；列表、详情、事件和审计均不得暴露 IP 网段、安装标识哈希或内部相关性键。
- 管理员/审核员必须在 MFA 会话中读取和处置告警；状态转换要求 `Idempotency-Key`、受控结果码和请求号，并写入不可变告警事件。
- 告警只提供运营提示和人工处置，不自动封禁账号或扣减信誉。候选内关联图谱与动态降权在 M4 第 6 次迭代完成，SLA/指派/事务通知在第 7 次迭代完成，签名 Webhook、投递指标和失败重放在第 8 次迭代完成，SMTP 邮件通道在第 9 次迭代完成；跨候选全局图谱和自动处罚仍属于后续范围。

M4 第 6 个关联证据与动态降权切片采用以下约束：

- `correlation-v1` 只在单个候选范围内构建反馈图：当前有效反馈只要共享安装标识哈希或 IP 网段即连边，并通过并查集形成传递闭包关联组；空关联键不参与建边。
- 同一关联组对成功和失败分别独立限权：每个结果在组内最多贡献最高单条有效反馈权重；`verification-v2` 使用降权后的有效成功/失败权重和独立组数进行状态判断。
- 每次有效反馈材料发生变化时，在同一事务内追加一条 `evidence_correlation_assessments` 聚合快照，绑定触发反馈，保存规则版本、组数量、降权数量及原始/有效权重；该表不得保存原始 IP、安装哈希或关联键。
- MFA 候选详情可展示脱敏后的账号/反馈标识、关联信号类型（`installation`/`ip_prefix`）和聚合权重，用于人工调查；不得返回原始 IP、安装标识哈希或内部关联值。
- 本轮仅处理候选内关联，不执行跨候选/全局身份图谱、自动封禁或自动扣减信誉；后续处罚必须经过独立规则、人工授权和不可变事件审计。

### 6.9.1 风险告警值班闭环实施增量

M4 第 7 次迭代将失败激增告警扩展为以下强制约束：

- `risk-alert-sla-v1` 以告警检测时间为基准，要求 15 分钟内首次响应、240 分钟内解决；告警保存规则版本和绝对截止时间，规则升级不得改写历史告警。
- 可指派人员仅限状态正常、角色为 moderator/admin 且启用 TOTP 的用户；负责人变化必须写入不可变事件。
- 检测、指派、响应超时、解决超时、解决和重开通知必须先与业务事件同事务写入 Outbox，再由 Worker 有限重试投递。
- 通知与管理响应不得包含密码、候选秘密、原始 IP、安装标识哈希、关联键或接收邮箱；接收地址仅在投递时读取。
- 管理队列必须支持负责人和 SLA 超时筛选，详情必须展示规则版本、截止时间、首次响应、负责人、事件和通知状态。
- 当前不包含排班表、升级链、动态 SLA 配置或自动账号处罚。通用签名 Webhook 在第 8 次迭代实现，SMTP 邮件在第 9 次迭代实现，但 staging/production 真实端点、SMTP 服务商、发件域名、凭据轮换、网络白名单和数据处理协议仍需环境验收。

### 6.9.2 通知投递运维实施增量

M4 第 8 次迭代将风险告警通知扩展为以下强制约束：

- 通知后端通过统一网关选择 `memory`、`log`、`webhook` 或 `smtp`；Webhook 仅允许 HTTPS，签名密钥至少 32 字符，网络超时限制为 1～30 秒。
- `notification-webhook-v1` 使用字段排序的紧凑 JSON、UTC 秒级时间戳和 HMAC-SHA256；签名输入为 `timestamp + "." + body`，接收方可返回提供商消息 ID。
- 投递记录保存提供商、提供商回执、失败时间、重放次数、最近重放时间和操作者；不得保存接收邮箱、Webhook 地址、签名密钥或原始载荷。
- 第三次投递失败进入 `failed` 终态。MFA 审核员/管理员只能重放失败记录；重放必须有 `Idempotency-Key`、原因和端点限流，并复用原 Outbox 记录及 `dedupe_key`。
- 管理端必须提供状态总量、近 24 小时失败数、最老待发送时长、按提供商聚合和失败队列；重放前后的状态及失败摘要必须进入最小披露审计。
- staging/production 真实通知端点、凭据轮换、网络白名单、提供商回调验签、Prometheus/OpenTelemetry 指标导出、多渠道路由和水平扩展压测留待后续验收。

### 6.9.3 SMTP 邮件投递实施增量

M4 第 9 次迭代将账号令牌和风险告警接入标准 SMTP，采用以下强制约束：

- `smtp` 后端必须支持 `starttls`、`ssl` 和仅限 `local/test` 的 `none`；非本地环境必须启用加密并同时配置用户名和密码。
- TLS 使用系统信任链和主机名校验；端口范围为 1～65535，连接超时限制为 1～30 秒。
- SMTP 密码必须使用秘密类型保存，只能由环境或部署秘密管理系统注入，不得进入日志、响应、数据库、审计或 Markdown 示例。
- 首版只发送 UTF-8 纯文本邮件。账号邮件仅包含一次性令牌、用途和安全提示；风险告警邮件仅包含告警 ID、通知类型、严重级别和处理时限。
- 每封邮件生成 RFC Message-ID。风险告警将其记录为 `provider_message_id`；该状态仅表示 SMTP 会话接受，不得解释为最终送达、打开或点击。
- SMTP 投递复用现有风险通知 Outbox、三次失败终态、指标和幂等人工重放，不新增邮件正文、收件地址或 SMTP 凭据持久化。
- 生产上线前必须在选定服务商环境完成 SPF、DKIM、DMARC、发件域名、配额、退信/投诉处理和凭据轮换验收；账号令牌事务 Outbox、送达回调和抑制名单留待后续。

## 7. 业务规则与数据质量

### 7.1 可见性规则

| 状态 | 匿名用户 | 注册用户 | 管理员 |
|---|---|---|---|
| pending | 仅显示存在待验证记录 | 可见遮挡候选，默认不可揭示 | 可查看与审核 |
| verified | 可见存在与可信标识 | 按配额揭示 | 可查看完整证据 |
| quarantined | 不展示 | 提示暂不可用 | 可调查与处置 |
| rejected | 不展示 | 仅贡献者可见原因 | 可查看历史 |

### 7.2 去重与冲突

- 指纹唯一键为 `(algorithm, digest)`；一个压缩包可有多个指纹。
- 候选密码使用服务端密钥化摘要做去重，不能在数据库中以明文唯一索引。
- 相同指纹对应多个密码属于“候选冲突”，不能简单覆盖；各候选独立维护证据和状态。
- 管理员合并或拆分记录必须记录源记录、目标记录、原因和操作者。

### 7.3 删除与保留

- 明文查询审计、认证日志和管理员审计采用独立保留策略。
- 用户删除请求先进入冷静期；内容如因合规、争议或安全调查需要保留，应进行去标识化并限制访问。
- 备份中的删除通过备份生命周期完成，不承诺即时物理擦除，但必须停止在线可见和业务使用。

## 8. 信息架构与关键页面

### 8.1 Web 用户端

- 首页：品牌、指纹输入/文件拖拽、模式说明、数据统计、授权提示。
- 查询结果：指纹、文件元数据摘要、候选列表、可信状态、证据计数、揭示与反馈。
- 贡献向导：选择文件/输入指纹、输入密码、本地确认、元数据与授权声明、预览提交。
- 用户中心：概览、贡献、反馈、积分与信誉、会话与安全、隐私请求。
- 帮助中心：指纹解释、合法使用规范、支持格式、隐私说明和举报。

### 8.2 视觉规范

- 用户 Web 采用“简白科技感 + 专业数字取证”视觉语言，避免暗黑压迫感和过度娱乐化；管理端可保持更高信息密度的独立主题。
- 页面以低饱和蓝白、灰白为基础，使用蓝紫作为主要交互色；成功、警告、错误和信息状态必须同时使用文字或图形语义，不能只依赖颜色。
- 顶部导航、主面板、卡片和浮层采用半透明浅色表面、细描边、柔和投影与毛玻璃背景模糊；不支持 `backdrop-filter` 时必须回退为高不透明度浅色表面，确保内容清晰可读。
- 用户可在内置浅色科技背景之间切换，并可选择本地图片作为当前会话背景；本地图片不得上传服务端或写入业务数据，刷新或离开页面后释放对象地址。
- 背景变化不得降低正文、表单、状态和焦点指示的可读性；正文原则上不小于 14 px，辅助标签不得承担关键业务信息。
- 键盘操作、可见焦点、减少动态效果偏好和移动端触控必须受支持；PC、平板、移动端断点分别为 ≥1200、768–1199、<768 px，核心查询流程在移动端保持单列。

| audit_logs | id, actor, action, target, result, ip_prefix, created_at | 管理与敏感操作审计 |
| reauthentication_grants | id, user_id, session_family_id, purpose, token_hash, mfa_verified, expires_at, consumed_at, created_at | 高风险用户操作的一次性再认证凭据；只保存摘要，绑定会话族和精确目的 |
| system_settings | key, value_json, version, updated_by | 版本化系统配置 |

### 9.2 敏感字段要求

- `secret_ciphertext` 使用带认证的加密算法和分版本密钥；密钥不与数据库部署在同一位置。
- 日志、监控、错误追踪、消息队列和分析系统中禁止出现解压密码明文。
- 文件名元数据单独加密或严格最小化；默认查询响应不返回完整列表。
- IP 仅为风控所需保留，展示和分析采用截断或哈希化形式。

## 10. API 设计基线

### 10.1 通用约定

- 基础路径 `/api/v1`；JSON 使用 `snake_case`；时间统一 ISO 8601 UTC。

- OpenAPI 文档在开发和测试环境启用；生产环境按访问策略开放。

> M4 风险告警管理增量：`GET /admin/risk-alerts` 支持 `assigned_to_id` 和 `overdue`；`GET /admin/risk-alerts/operators` 返回可指派 MFA 操作者；`POST /admin/risk-alerts/{alert_id}/assign` 使用 `Idempotency-Key` 显式指派负责人；告警详情包含 SLA、负责人变化和通知投递状态。通知投递运维接口提供聚合指标、失败筛选和幂等人工重放，任何响应均不得返回邮箱、Webhook 地址、签名密钥或原始投递载荷。

> N2 审计中心增量：列表支持动作、结果、目标类型、操作者、请求号、时间范围和综合搜索；详情和 CSV 必须再次执行服务端递归脱敏与长度/深度限制。CSV 使用 UTF-8 BOM，防止公式注入，单次最多 5000 条，导出端点每分钟最多 10 次且导出行为写入不可变审计。列表和详情读取不额外写审计，避免自递归和无界噪声。

> N2 用户治理增量：`/admin/users` 与 `/admin/users/{user_id}` 仅允许 `admin` 角色且当前会话 MFA 已验证；列表和详情只返回脱敏邮箱、账号状态/角色、TOTP 状态、会话摘要、积分/信誉/贡献/案件/隐私队列计数，不返回密码、令牌、TOTP 密钥、IP 或秘密材料。停用、恢复、会话撤销和普通角色受控变更必须使用管理员专用近期再认证凭据，并同时满足当前密码、TOTP、结构化原因码、`Idempotency-Key`、乐观并发、对象级保护和不可变审计；停用或角色批准自动撤销目标活跃会话。管理员自身、其他管理员和服务账号受保护，批量处置继续关闭。

> N2 角色治理增量：受控角色变更先创建 `role_change_requests` 请求，再由不同管理员批准或拒绝；请求列表、创建、批准和拒绝接口要求当前会话 MFA、用户治理一次性再认证、结构化原因码、`Idempotency-Key`、状态/目标角色乐观并发和不可变审计。当前仅允许 `user`、`trusted_contributor`、`moderator` 之间的固定转换；批准后撤销目标账号活跃会话。Admin `/role-changes` 工作台已提供筛选、分页、详情、创建和双人批准/拒绝，并在敏感操作结束或上下文切换时清理密码、TOTP 与再认证令牌。管理员、服务账号、申请人自身、非正常账号、紧急撤权、批量处置和独立事件时间线继续关闭。

### 10.3 案件处置、通知和 SLA 规则

- `resolve` 是案件最终关闭的唯一原子入口：举报结果可为 `action_taken`、`no_violation` 或 `insufficient_evidence`；贡献申诉可为 `appeal_upheld`、`appeal_denied` 或 `insufficient_evidence`；账号申诉可为 `account_restored`、`account_restriction_upheld` 或 `insufficient_evidence`。
- `action_taken` 必须同时指定候选 `rejected`/`quarantined`，`appeal_upheld` 必须指定 `verified`；账号恢复只作用于案件服务端派生目标账号。所有副作用在同一事务内写入，并由 `trust_case_effects` 防止重复结算。
- 新建举报/贡献申诉默认 96 小时 SLA，账号申诉默认 72 小时 SLA。Worker 每 60 秒扫描逾期的 `open`/`in_review` 案件，单案写入一次 `case.sla_escalated` 不可变事件并递增升级计数。
- 最终处置事件生成去重通知 Outbox；Worker 每 15 秒投递，失败最多 3 次，管理员可在 MFA 和幂等保护下重放。通知只包含案件编号、类型、状态和结构化结果码。

## 11. 技术架构

### 11.1 统一技术路线

- 用户端与管理端：Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus。
- 后端：Python、FastAPI、SQLAlchemy、Alembic，采用模块化单体而非 PHP/Go/Python 多语言微服务。
- 数据库：MySQL 8 系列；精确指纹查询使用唯一索引，无需在 MVP 引入 Elasticsearch。
- 缓存与任务：Redis；耗时通知、批处理和维护任务使用可横向扩展的 Celery Worker，周期任务由单独 Celery Beat 调度实例负责，禁止每个 Worker 副本同时携带 Beat；Worker 并发必须显式配置并纳入数据库连接池容量预算。
- 桌面端：C#、WPF、.NET 10 LTS；网络层使用 `HttpClientFactory`，本地密钥使用 DPAPI；更新发现和升级下载由后端发布模块统一提供。
- 网关与部署：Nginx、Docker Compose 起步；生产数据库优先使用托管服务或独立高可用部署。
- 质量与运维：pytest、Vitest、Playwright、xUnit/NUnit、OpenTelemetry、Prometheus/Grafana 或等价托管方案。

### 11.2 逻辑架构

`Web/管理端/桌面端 → Nginx/API 网关 → FastAPI 模块化单体 → MySQL`

FastAPI 同时访问 Redis（缓存、分布式限流、任务代理）和关系数据库（业务数据、审计、持久化幂等）；Celery Worker 处理通知、批量任务、数据清理和报表，单独 Celery Beat 实例负责周期调度。Worker 使用实例级 TTL 心跳并只导出聚合数量；Worker 并发必须显式配置，MySQL 连接池必须按 API 进程、Worker 副本与并发、Scheduler 等全部数据库客户端进程配置和核算。密码加解密通过独立密钥管理接口完成。桌面发布制品在开发环境写入受控本地目录，生产发布前必须迁移到持久卷或对象存储适配器并通过 HTTPS/CDN 分发。监控采集 API、队列、数据库和系统指标。

## 12. 安全、隐私与风控

### 12.1 认证与授权

- 访问令牌短期有效；刷新令牌轮换、可撤销、检测重复使用。
- 管理端使用独立入口、RBAC 和 TOTP；危险操作要求再次验证。
- 服务账号和任务账号不共享管理员凭据。
- 对对象级访问进行统一授权检查，避免通过修改 ID 访问他人贡献、任务或审计数据。

### 12.2 API 防护

- 登录、注册、揭示、贡献、回执和反馈分别限流，不使用单一全局阈值。
- 限流维度组合账号、安装实例、IP 前缀和行为风险；返回标准 `429` 与重试时间。
- 所有输入使用模式校验；限制请求体、列表长度和字段长度。API JSON 请求体默认上限为 1 MiB，可配置范围为 1 KiB～16 MiB，并必须按实际接收字节阻断分块传输绕过；桌面二进制制品使用独立流式上限。
- CORS 使用明确域名白名单；生产禁用调试信息；安全响应头由 Nginx 和应用共同保证。API 至少返回 `nosniff`、禁止嵌入、最小 Referrer、受限 Permissions Policy，并对未声明缓存策略的 API 响应默认 `no-store`。

### 12.3 数据保护

- 账号密码强哈希；解压密码因业务需要可逆，但必须应用层加密、密钥轮换和访问审计。
- 候选秘密使用版本化 AEAD 密钥；新写入只使用当前版本，读取在受控回滚窗口内允许历史版本。加密密钥轮换不得改变稳定 HMAC 去重标签，密钥材料必须与数据库和代码仓库分离。
- 备份加密并定期恢复演练；不同环境使用不同密钥和数据。
- 测试环境禁止复制生产解压密码；使用合成数据。
- 敏感字段在日志、追踪和错误报告中自动脱敏。

### 12.4 威胁场景

重点覆盖：批量枚举密码、凭据填充、对象级越权、桌面回执伪造、重放攻击、关联账号刷票、管理员滥权、数据库泄露、密钥泄露、日志泄密、依赖供应链、恶意压缩包导致客户端资源耗尽。

## 14. 测试与验收基线

### 14.1 测试层级

- 单元测试：指纹校验、状态机、积分账本、风险权重、加密封装。
- 集成测试：数据库约束、Redis 限流、令牌轮换、幂等、任务重试。
- 契约测试：OpenAPI 与 Web/桌面生成客户端的一致性。
- 端到端测试：注册→计算指纹→查询→贡献→桌面验证→状态变更→揭示。
- Web/Admin 浏览器验收使用 Playwright Chromium、每轮重建的隔离数据库和合成账号；不得读取开发者本地数据库。
- 无认证材料的场景失败时保留截图、Trace、控制台和请求证据；含密码、访问令牌或 TOTP 密钥的认证场景必须关闭网络 Trace/截图或先完成可靠脱敏。
- 安全测试：越权、重放、刷票、枚举、敏感日志、恶意文件、依赖漏洞；至少包含普通用户跨用户对象边界、浏览器 Cookie CSRF/SameSite/路径隔离、管理员 MFA/再认证、幂等重放和资源消耗动态门禁。
- 恢复测试：数据库恢复、密钥版本读取、Redis 丢失、Worker 重启。

### 14.2 发布验收门禁

- 所有 MVP 需求有测试用例和验收证据。
- P0/P1 缺陷为 0；P2 有明确责任人与修复计划。
- 不存在未处置的高危依赖漏洞或高危渗透测试发现。
- 完成数据库备份恢复、密钥轮换演练和回滚演练。
- 在 staging 持续执行至少 4 小时 API/MySQL/Redis/Celery 混合负载，满足版本化操作量、错误率、连续错误、P95、CPU/内存峰值、采样覆盖和队列清零阈值，并在单 Worker 故障期间保持整体可用；资源趋势报告必须通过 `staging-resource-trend-report-v1` 校验。
- 完成 MySQL/Redis 高可用切换并记录 RTO/RPO、主节点变化、应用恢复、数据/队列完整性、幂等和回滚就绪检查；报告必须通过 `staging-ha-failover-report-v1` 校验，standalone/single 模式不得作为生产高可用证据。
- 目标环境资源证据应通过 `staging-prometheus-range-export-v1` 导入规范化单序列 Prometheus 区间数据；MySQL/Redis 平台事件应通过 `staging-ha-platform-export-v1` 导入，并仅保留允许的 HA 生命周期、持久点和原始事件 SHA-256。跨序列时间错位、原始平台事件 ID、凭据、端点或未批准字段必须被拒绝。
- 数据库连接池预算必须覆盖所有 API、Worker 与 Scheduler 客户端进程，显式 Worker 并发或副本变化后必须重新计算。
- 隐私政策、服务条款、授权声明、举报与删除流程已上线。
- 监控面板、告警联系人、值班手册和故障预案可用。
- 技术负责人、安全负责人、运维负责人和业务负责人基于同一证据包完成 Go/No-Go；证据包必须通过 `staging-execution-evidence-bundle-v1` 的 profile SHA-256、敏感字段和 checksum 校验，且 `contract-fixture`/`target-execution` 边界清晰；交接前还必须通过 `staging-evidence-archive-manifest-v1`，绑定候选提交 SHA 和确定性 ZIP，静态合同或封存通过不得替代目标环境执行和签字。

## 15. 统一决策与原文冲突处理

| 原文冲突 | v3.0 决策 | 原因 |
|---|---|---|
| “文件哈希→明文”与“密码哈希反查”混用 | 统一为压缩包文件指纹→解压密码 | 文件指纹不能由密码计算得到 |
| 提交时校验 `hash(password)==file_hash` | 删除该规则，改为本地解压证据 | 原规则技术上错误 |
| User-Agent/硬件 ID 代表桌面可信 | 安装密钥+挑战+签名+风控，不采集硬件序列号 | UA 可伪造，硬件 ID 有隐私问题 |
| pending/preliminary/desktop_verified 混用 | 状态统一为 pending/verified/quarantined/rejected；来源与证据分字段 | 状态与来源解耦 |
| 查询次数达到阈值自动验证 | 禁止；查询量仅用于热度 | 命中不证明密码正确 |
| 信誉分初始值 0 或 100 | 统一为 50，0–100 | 便于上下浮动并避免历史冲突 |
| PHP+Go+Python 与纯 FastAPI 冲突 | MVP 使用 FastAPI 模块化单体 | 减少团队与运维复杂度 |
| Tauri/Electron/C# 冲突 | Windows 首版统一 C# WPF | 与现有桌面端专项文档一致 |
| Elasticsearch 作为必选 | 移出 MVP | 核心查询为精确索引，不需全文搜索 |
| 自动导入公开泄露口令库 | 禁止进入产品范围 | 合规、滥用与数据安全风险过高 |
| 论坛/商城/悬赏与核心同时开发 | 移到后续独立立项 | 控制首版范围和关键路径 |
| 文件名逗号拼接 | 结构化数组、最小化、去路径、默认不公开 | 隐私、安全和可扩展性 |
| JWT 中写入动态权益 | 权益实时查询或短缓存 | JWT 不适合承载频繁变更状态 |

## 16. 风险登记

| 风险 | 概率/影响 | 预防与应对 |
|---|---|---|

## 附录 A：术语

- **指纹**：用于识别压缩包文件的哈希摘要，不是解压密码的哈希。
- **揭示**：把加密保存的候选密码解密并返回给已授权用户。
- **证据**：支持候选密码成功或失败的独立事件。
- **隔离**：发现高可信冲突后暂时停止公开候选密码。
- **规则版本**：每次自动判定状态时记录的验证规则版本，保证可复盘。
